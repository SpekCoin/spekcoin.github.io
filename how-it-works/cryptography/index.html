How it works

Cryptography

Every signature in Spek is SQIsign, an isogeny-based post-quantum scheme, and every hash is BLAKE3. Two facts qualify everything on this page.

SQIsign is not a NIST standard

SQIsign is a Round 3 candidate in NIST's additional-signature process (advanced in May 2026, with about two years of evaluation ahead). "NIST security level 1" names a security category, not an approval.

Audited only by AI models

The founders used Claude AI models to build and audit Spek, and the code has been audited only by AI models (Claude). No independent human audit, cryptographer review, or SQIsign-author review took place before launch. Anthropic, the maker of Claude, is not a partner in this project and does not endorse it.

Why SQIsign, and what if it fails

NIST advanced nine candidates to Round 3 of its additional digital-signature process in May 2026; one of them, HAWK, has since been withdrawn by its submission team, leaving eight, and SQIsign is among them. That round is expected to last about two years, a draft standard could not appear before about 2028, and SQIsign may be dropped. "Level I" and "Level V" name the security categories its parameters target, comparable to AES-128 and AES-256 key search, not any NIST approval.

Spek chose SQIsign over the standardised ML-DSA for its size: a 200-byte signature and an 83-byte key, against roughly 2.4 KB and 1.3 KB. The trade-off is that SQIsign's security rests on a younger assumption, the supersingular endomorphism-ring problem, with less cryptanalytic history than lattices, and on a reference implementation that was not built for production.

If later cryptanalysis weakens SQIsign, or NIST drops it, the only remedy is a migration to another signature scheme through a hard fork, and every operator chooses for themselves whether to adopt it. Mining keys rotate with every horizon, so moving block headers to a new scheme phases in as horizons expire, with no coin moves.

Level I and Level V

LevelPublic keySignatureSecret keyVerify (ADX / portable)Used for
I83 B200 B270 B2.68 / 5.03 msHeaders, mining keys, stake outputs, everyday outputs (the default)
V169 B406 B549 B16.4 / 26.7 msOpt-in custody outputs; every genesis allocation, council and guardian key

Signing a Level I header takes 25–40 ms, once per slot for a miner. There is no ECDSA, no Schnorr and no elliptic-curve library linked into the signature code, and a test on the dependency graph keeps it that way.

Why headers stay at Level I

Someone who broke Level I still could not win a live slot as someone else: they would also need that key's unrevealed slot secret, which comes from an independent slot seed and is protected only by BLAKE3. They could copy a just-revealed slot secret into a second header and force the slot to be forfeited, a liveness attack rather than a theft, and they could sign branches for past heights down to the restoration pin, which would hold at any level that broke.

Keys hidden until spent

The default output hides even the public key. A hashed output is 34 bytes: a witness version and a 32-byte program, which is a tagged BLAKE3 hash of the key and its script commitment. The key appears on chain only when the output is spent. Wallets use this form for every receive, change and coinbase address. The one exception is a stake key, which every header it signs makes public; the payout rule keeps one stake unit at that address.

ScriptCommit instead of Taproot tweaks

Taproot hides a script tree by tweaking an elliptic-curve key. Isogeny keys cannot be tweaked that way, so Spek's analogue, ScriptCommit, commits to the script tree with a hash instead. A key-path spend reveals the key and commitment next to one signature; a script-path spend reveals the leaf, its Merkle proof and a control block, and the node recomputes the commitment and the program before running the leaf. Multisig, timelocks, hash locks and atomic swaps are expressible; key aggregation is not. An output that wants its key visible can use the plain ScriptCommit form, 118 bytes.

Addresses

Addresses are Bech32m with the prefix spek. Witness version 1 carries a 32-byte hashed program (Level I) or the 115-byte plain program, and version 2 a 32-byte Level V program. Decoding re-encodes and requires a byte-exact match, so each output script has exactly one lowercase address string. There is no pay-to-pubkey form.

Slot secrets from BLAKE3 alone

The election needs a per-slot value that is secret until used, unique per height and committed before the beacon exists. No deployable post-quantum VRF exists, so Spek builds it from BLAKE3 hash chains (see Slot election). The slot seed is independent of the signing key, so recovering a SQIsign secret key reveals nothing about future slot secrets. Every consensus hash is domain-separated by a tag string.

Worth a cryptographer's time

The election is only fair if each key has exactly one valid slot secret for each height. If a miner could find two valid secrets for the same height, it could try both and keep the better score, which is the cheating the design exists to prevent. This one-valid-secret property is what Spek's hash chains are built to guarantee, and it is the part most worth an outside expert checking. It matters because X-VRF, another hash-based scheme designed for electing block producers, was published and then broken, and the break was on exactly this property. Spek's construction is different, but that is the history, and no human cryptographer has yet reviewed it.

The migration path

If SQIsign is ever weakened, Spek has to be able to switch to a different signature scheme. This is how the switch is built to work.

  • Every output carries a version number that names the scheme that must verify it: 1 is Level I, 2 is Level V, and 3 to 16 are held back for future schemes.
  • Every block header also carries a version, and the version decides which scheme signs the header. A new header scheme starts at a block height set in advance in an upgrade schedule.
  • At any height, only one scheme is valid for a given version. There is no list of algorithms to choose from, so an attacker cannot talk a node into accepting a weaker one (a downgrade attack).
  • A signature covers the locking script of every output it spends, so a signature made for one scheme cannot be reused as if it belonged to another.

Adding a new scheme is a hard fork: every operator chooses whether to adopt it. Block headers move over without anyone moving coins, because mining keys are replaced with each new horizon.
