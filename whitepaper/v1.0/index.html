Spek

A post-quantum, unbonded proof-of-stake ledger with a secret election every 30 seconds and no retries.

Technical white paper, November 2026. Describes the reference implementation (Rust, MIT / Apache-2.0). Designed by the founders, implemented, tested and reviewed entirely by Claude Code.

Abstract#

Spek is a blockchain ledger in which time, not computing work, schedules blocks. The clock is divided into 30-second slots counted from a genesis timestamp, and every slot gets exactly one block. Each eligible stake address gets one secret draw per slot: a score that only the key's owner can compute, from inputs that were all fixed before the randomness it is drawn against existed. The highest score whose block is valid wins the slot. Nobody can predict the winner before its block header is published, and nobody can improve a draw by trying again, because there is nothing to try again. If no valid candidate arrives, every node builds the same null block, a block with no transactions, so a slot without a winner does not stop the chain.

Taking part costs a held balance, not a power bill. Once the 45-day launch phase is over, a key can win blocks while its stake address holds one output worth at least 80% of the block reward that is at least a day old. The output stays an ordinary coin: nothing is locked, nothing is slashed, and spending it ends eligibility. During the launch phase nobody holds coins yet, so eligibility is bought with RandomX computation instead: one recorded ticket per key per 3-day round.

Every signature is SQIsign, a compact post-quantum scheme, and every hash is BLAKE3. Public keys stay hidden behind hashes until coins are spent. Nodes take their time from an authenticated Roughtime quorum rather than the host clock. Transactions are confirmed by a depth sized to an assumed attacker share, and checkpoints bound how far history can be rewritten. Supply is capped at 450,000,000 coins: a 30,000,000-coin genesis allocation (founders 5%, vesting over five years; a stewardship fund 1.67%, vesting over twenty) plus a 50-coin block reward that halves every 4,200,000 blocks (about four years).

1. Introduction#

Every open blockchain has to decide who adds the next block, in a way an attacker cannot cheaply take over. Proof-of-work buys Sybil resistance (resistance to one party posing as many) with energy, and rewards whoever burns the most. Bonded proof-of-stake buys it with locked capital, and inherits a thicket of slashing, validator sets, and finality gadgets to police that capital. Spek is unbonded proof of stake: a per-slot election over stake outputs that each meet a coin threshold, with nothing locked and nothing slashed.

Three ideas carry the design:

  1. Time is the schedule. A block exists for every 30-second slot since genesis, whether or not anyone produced one. Height, timestamp, reward, fee floor, coin requirement and the unlock height of each genesis allocation tranche (its vesting) are all functions of the slot number.
  2. One stake output, one secret draw. A miner's score for a slot is its hash distance against that epoch's random beacon, which is read from the chain's election seed (built block by block from the previous block's seed) long before the epoch starts. Everything else in the score was fixed before the beacon existed: the miner's key, a secret it committed for that slot, and the height. There is no nonce to grind, no key to swap in after the fact, and nothing a miner can re-sign or re-order to improve its own or any later chance. Until a miner publishes its header, nobody else can compute its score.
  3. Eligibility is the security parameter. However the winner is picked from independent, uniform draws, a party holding N of the N+H draws in play (H being everyone else's) wins exactly N/(N+H) of the slots: its share of the draws is its share of the blocks. So the only lever left is what a draw costs to field, and Spek prices that explicitly, in two phases (§7).

Stake in Spek is a threshold met by one ordinary output, never a bond: nothing is locked, burned or slashed, there is no validator set and no delegation, and there is no yield. The block winner earns the block reward. For the first 45 days eligibility is priced with RandomX tickets instead (§7.2); that work buys eligibility for a round, never a block, so the chain is not proof of work even then. The result is a network whose honest operating cost is a node and a held balance.

1.1 One slot, start to finish#

  1. A new slot opens every 30 seconds. Its number is the height of the block it will produce.
  2. Each miner with an eligible key (§7) computes its score for the slot: one hash of the epoch's beacon, the height, its public key and its draw secret for that height (§4).
  3. For the first 6 seconds only block headers travel. Each node ranks the headers it receives by score.
  4. From 6 to 30 seconds nodes fetch the full blocks of the best few candidates and validate the best one.
  5. When the slot closes, each node commits the highest-ranked candidate whose full block is valid. If there is none, every node builds the same null block (§5).
  6. The winner's draw secret is mixed into the chain's election seed, from which a later epoch's beacon is read (§4.2).

2. Design goals#

  • Post-quantum by construction. SQIsign for every signature (Level I for headers and everyday outputs, Level V opt-in for long-lived custody), keys hidden behind hashes until spent, no elliptic-curve code in the signing code, and a versioned migration path (§8.5).
  • No computational waste. One BLAKE3 evaluation per stake output per slot decides candidacy; producing the draw secret costs fewer than 96 hashes. Signing costs 25–40 ms once per slot; verifying a header costs one SQIsign verification (2.7–5.0 ms) plus a walk of at most 8,651 hashes (0.9–2.6 ms).
  • Unpredictable election with no retries. Every score input is fixed before the beacon it is drawn against exists, and each winner adds secret entropy to a later beacon. No winner schedule exists to read ahead of time, so there is no predicted winner to target.
  • Deterministic everything. Timestamps, rewards, tie-breaks, null blocks and genesis bytes are identical on every node. SQIsign signatures are randomised, so the protocol keeps them out of everything that must be deterministic.
  • Plain confirmation claims. Forks near the tip are compared within a 4-block window (about 2 minutes). Transactions are confirmed by a depth sized to an assumed attacker share (Appendix B), and a running node never reorganises below its restoration pin (33–67 h). There is no finality gadget.
  • Fail fast. Cheap structural checks reject bad input in microseconds; expensive checks run only on the top-ranked candidates.
  • Plain governance. One upgrade mechanism (header version and flag height), no on-chain voting, a published multisig council for the stewardship fund.

2.1 Security claims#

What Spek claims, and under what assumptions, in one place. Each claim points to the section that argues it.

Assumptions. SQIsign Level I and BLAKE3 are secure (§8). Honest nodes take their time from a Roughtime pool whose operators are mostly honest (§3.3); colluding operators can walk a node's clock by at most 5 s per sync (§17). Headers reach honest nodes within the 6-second headers-only phase and bodies within the 24-second block phase (§3.2). The attacker holds a share q of the draws in play, a fraction of all funded stake addresses after the launch phase and of recorded tickets during it (§7).

Claims.

  1. Unpredictable winners. Nobody but a key's holder can compute its score before its header is published (§4.1, §4.3).
  2. No retries. For each stake address (key, horizon root and horizon start) and height exactly one draw secret verifies, so a miner cannot improve its score by trying again (§4.1, §4.7). The argument reduces a second verifying draw secret to a BLAKE3 collision (§4.8).
  3. Bounded beacon bias. A miner's only informed influence on a beacon is withholding blocks at the end of the beacon's source epoch, worth 1.9–3.0% of its own wins in an epoch it controls and 0.3–0.6% averaged over all epochs, with no compounding (§4.2). Withholding earlier in that epoch changes the beacon blindly.
  4. Blocks in proportion to draws. A party with share q of the draws wins share q of the slots (§1, §7.3).
  5. Confirmations. Against q = 1/3, 223 confirmations (1.9 hours) keep reversals under one slot per century; Appendix B gives the depth for q up to 0.40. The model assumes the attacker's branch shares the honest chain's beacons, which holds for its first 1,441 blocks. Forcing null blocks on the honest chain gains an attacker nothing below about q = 0.44 (§6.1).
  6. Rewrite bounds. A running node never reorganises below its restoration pin (33–67 h deep). A private branch inside the pin gains on the honest chain only above an attacker share of 0.44–0.46, and a fresh node with no checkpoint past the fork is safe only below about 0.38 (§17).
  7. Liveness. Every slot ends with a block, a null block if no valid candidate arrives (§5). An attacker can force a null only by holding all five of a slot's best headers and withholding their bodies, about q⁵ of slots (§17), and below about q = 0.44 doing so does not help a private branch (§6.1).

Working assumption. Spek is designed to be safe for q < 0.38, and its confirmation guidance is sized for q ≤ 1/3 (223 confirmations). Above 0.38 the protocol makes no safety claim for nodes without recent checkpoints.

Not claimed. Fast finality; safety above half the draws; security once rewards stop and only fees pay miners (§17); any guarantee for a node that trusts no checkpoint (§12.3).

3. Timeslots and the verified clock#

3.1 Slots#

With genesis timestamp G, the slot being mined now, which is also the height of the block that does not exist yet, is

current slot       = ⌊(now − G) / 30⌋        unsettled: being mined
settled tip        = current slot − 1        the newest block that can exist
timestamp(h)       = G + 30·h

The header has no timestamp field: a block at height h can only have timestamp G + 30h. That removes timestamp manipulation, median-time-past rules and tolerance windows by construction. Block height is a u32 (about 4,000 years of 30-second slots); derived timestamps are 64-bit.

Slots are grouped into epochs of L = 1,440 slots (12 h), which carry the election beacon (§4.2), and segments of S = 8,640 slots (3 days), which carry each key's draw-secret hash chains (§4.1).

3.2 Two phases per slot#

Each slot has a headers-only phase (0–6 s), in which 743-byte candidate headers flood the network and the ranking settles, and a block phase (6–30 s), in which nodes fetch full blocks only for the top three candidates and serve the top five. The best candidate (rank 1) decides the slot, so its body is requested from up to three peers at once; ranks 2 and 3 are backups and are requested from one peer each. Headers keep propagating throughout the block phase: a late header can still enter the ranking, and the top three are re-derived whenever it changes. Because bodies move only after the ranking is known, unranked blocks cannot waste bandwidth. Ranks 4 and 5 are normally never fetched: a node pulls one of them as a backup only when a top-three body proves unfetchable, so that it still has a committable body at the boundary (§5). The 24-second body window fits megabyte-scale blocks crossing intercontinental links, with room for two retry rounds.

0 s                6 s                                                   30 s
|--- headers only --|--- pull top-3 bodies · validate rank-1 · serve top-5 ---|
slot h opens                                        boundary: winner of h committed, or null

3.3 Where time comes from#

A wrong clock puts a node in the wrong slot, so Spek does not take consensus time from the operating system. Each node keeps its own verified clock:

  • Source. Roughtime, an authenticated time protocol. Every response is authenticated end to end: the server's long-term Ed25519 key signs a delegation certificate, the delegated key signs the response, the node's own request is bound into the signed reply (so a recorded reply cannot be replayed), and the reported time must sit inside the delegation's validity span.
  • Quorum. Servers are queried in parallel and every sample is corrected for round-trip time. Each operator (whoever holds the keys) casts one vote, the median of its own samples, however many addresses it runs. Votes more than 2 s from the median of votes are discarded, at least 3 voting operators must remain (a node may be set to require more, never fewer), and the median of the surviving votes is adopted, rounded to whole seconds.
  • Between syncs. Verified time is carried forward on the raw hardware oscillator, not on the system clock the host's NTP daemon adjusts. Raw oscillators run 30–100 ppm (parts per million) off on ordinary and cloud hosts, so the node learns its oscillator's rate from successive syncs and corrects for it. Each sync may move the learned rate by at most 50 ppm, and the rate is clamped at 250 ppm, so a steered quorum cannot install a large false rate in one step.
  • Cadence. A node syncs hourly while it learns its rate, and every 6 h once a sync confirms the rate to within 5 ppm (at most about 108 ms of drift over the interval). A sync falls due after that time and runs at the node's next 40-minute check, so syncs land 6 to 6 h 40 min apart once the rate is settled, and 1 to 1 h 40 min apart while it is learned. A sync that shows the rate has changed (a migrated virtual machine, for example) drops it back to hourly.
  • Step bound. A new median is accepted outright only within 5 s of where the node's clock already is. A larger step, forward or backward, is refused unless it is corroborated, either by the node's own measured drift against its system clock (the suspend-and-resume case) or by a second sync, at a higher quorum, that agrees with the refused one. One bad answer therefore cannot move the clock, and a node that is genuinely off still converges. The first sync after boot has no clock to bound against and is always applied.
  • Mining hold. A node that has never acquired a verified time does not sign blocks. Relaying, serving and syncing continue. An opt-out exists for the case where every configured server is down, and it is loud.

Consequence. Agreement between nodes' clocks is bounded by the residual after rate correction over one sync interval plus Roughtime path asymmetry, not by a "sub-second" promise. The 2-second outlier bound, the 5-second step bound and the 30-second slot are sized around that.

How far clocks can differ. After a sync a node's error has three parts: the rate residual (at most 5 ppm over 6 h, 108 ms), the round-trip correction (at most half the round trip to a server, under 200 ms for a 400 ms round trip), and the operators' own accuracy, which is trusted. Two honest nodes with confirmed rates can therefore differ by well under a second (about 0.6 s in the worst case for 400 ms round trips), against a 6 s headers-only phase and a 24 s body phase. A node still learning its rate syncs hourly, so its residual is up to about 0.36 s (100 ppm over an hour); two such nodes can differ by about 1.1 s, still well inside the headers-only phase. An early or late header is handled by the ranking and the boundary wait (§5), not by tolerance in the slot rule, which stays strict. The 2-second outlier filter removes a single faulty operator, but it cannot remove operators who collude, because together they move the median the filter is measured from. What limits them is the step bound: two colluding operators can move a node's clock by at most 5 s per applied sync (§17).

4. Leader election#

The election needs a per-slot value that is (a) secret until used, (b) unique per height, so it cannot be grinded, and (c) committed before the randomness it is drawn against exists. Spek builds it from BLAKE3 alone, with committed hash chains.

4.1 Draw secrets and horizons#

Each miner key file holds a SQIsign Level I key pair (a 270-byte secret key and an 83-byte public key) and a 32-byte draw secret root, 385 bytes in all. The draw secret root is drawn from the operating system's cryptographic random generator when the key is generated, the same source SQIsign key generation uses. The draw secret root is independent of the signing key, so recovering a SQIsign secret key reveals nothing about future draw secrets.

σ       = BLAKE3-derive-key("spek 2026-10-20 draw-secret v1", draw_secret_root)
s_g     = BLAKE3("spek/slot-chain/v1" ‖ σ ‖ g)                 // one chain per 3-day segment g
T_g     = step^S(s_g)                                          // segment top, step = BLAKE3("spek/slot-step/v1" ‖ x)
r_h     = step^(S − 1 − (h mod S))(s_g(h))                     // draw secret for height h
leaf_j  = BLAKE3("spek/slot-leaf/v1" ‖ pk ‖ T_(J0 + j))         // j = 0 … 1023, key-bound
C       = Merkle root over the 1,024 leaves                    // one horizon

Each segment's chain is revealed backwards, one value per slot, so publishing r_h exposes only values for heights already passed. A horizon is 1,024 consecutive segments starting at segment J0: about 8.4 years. Its root C is a 32-byte BLAKE3 hash, bound to the key in every leaf, and is committed in the stake output (§7.1) before any beacon it will be drawn against exists, so for every key, commitment and height exactly one r_h verifies.

A header carries the draw secret, its 10-hash Merkle path and J0. A verifier walks the draw secret up to its segment top (at most S hashes), hashes the key-bound leaf, climbs the path, and uses the root it derives to rebuild the stake address. If the draw secret is wrong, there is simply no stake at that address. The root itself is never carried. A mining node keeps the 1,024 segment tops (32 KB) and checkpoints within the current segment, so producing r_h takes fewer than 96 hashes; building a horizon takes 1–3 s.

A node creates its next horizon automatically about a year before the current one ends (122 segments by default, an operator setting), with two segments of overlap so eligibility never lapses.

4.2 The epoch beacon#

B_e = BLAKE3("spek/beacon/v1" ‖ e ‖ genesis.merkle_root)                 e ∈ {0, 1}
B_e = BLAKE3("spek/beacon/v1" ‖ e ‖ election_seed@beacon_height(e))      e ≥ 2
beacon_height(e) = (e − 1)·L − 1

The beacon for epoch e is read from the election seed at the last block of epoch e−2, a full epoch before e starts. Every block of that source epoch mixes its winner's secret r_h into the election seed (§4.4), so the beacon is unpredictable until the source epoch has been produced. It is the same on every fork that shares that history, which covers every fork near the tip (at most 5 deep, against L = 1,440).

Epoch e−1 sits between the beacon height and the epoch it serves on purpose. It puts every height of epoch e at least 1,441 blocks above the block its beacon is read from, so even a fork that straddles an epoch boundary shares that block, and nodes know the next epoch's beacon a full 12 hours early, so a header for the first slots of epoch e can be scored as soon as it arrives. Epoch e−1 is not idle: its own blocks feed the beacon of epoch e+1.

Epochs 0 and 1 read the genesis merkle root, which commits to the launch ticket records and a launch nonce derived from a Bitcoin block mined after the record list was sealed (§7.2), so nobody, the organiser included, could choose it knowing the launch beacons.

Every block of epoch e−2 feeds the seed, so withholding any of them changes the beacon. Only the end of the epoch gives an informed choice, though: a block withheld earlier is followed by blocks whose draw secrets the withholder does not know, so it changes the beacon to a value it cannot predict, a blind re-draw worth nothing on average and costing the withheld block's reward. The lever is at the beacon height. Its miner can withhold its block and let the runner-up set the beacon instead, and because it holds its own future draw secrets it can evaluate both choices; a miner that wins the last t blocks of the epoch has up to 2^t choices. Simulation (reference 10) puts the net gain, after the rewards of the withheld blocks, at 3.0% more of its own wins in the controlled epoch at an attacker share q = 0.1, 2.4% at q = 0.2 and 1.9% at q = 0.33, and 0.3–0.6% averaged over all epochs, since it controls a beacon only when it wins the epoch's tail. The gain does not compound: steering one epoch's tail to win more choices later costs the wins it would buy, and the expected number of choices, (1−q)/(1−2q), stays bounded below half the draws (at q = 0.45 the net share is 0.450 with steering against 0.453 without).

Every miner can compute its own scores for the whole of epoch e as soon as B_e is known, 12 hours ahead. That tells it when it is likely to win, which matters for the strategies in §17, but it cannot change any score.

4.3 The score, middle-out#

score = middle_out( BLAKE3("spek/score/v2" ‖ B_e ‖ h ‖ pk ‖ r_h) )
x = hash as a 256-bit integer,  M = 2^255 (the midpoint)
middle_out(x) = x ≥ M ? (x − M) + 1 : M − x          // range [1, 2^255], arbitrary-precision integers

Both 0x00…00 and 0xFF…FF score the maximum; 0x7F…FF and 0x80…00 score 1. The genesis block scores the fixed 2^255; a null block scores 0.

0x00…00                         M = 2^255                          0xFF…FF
|==================================|==================================|
score 2^255 (max)              score 1 (min)               score 2^255 (max)
            higher score = further from centre = more likely to win

The shape of the score is a convention, not a security choice. A uniform 256-bit hash maps to a score that is uniform over [1, 2^255] (every score is reached by exactly two hashes), so the winner's odds depend only on how many draws each party holds, and a rule that ranked the raw hash value would give the same odds. Measuring distance from the centre puts the maximum at both ends of the hash space and a single minimum in the middle, which is what fixes the edge cases above exactly.

Every input is fixed before the beacon exists: the key and its horizon root sit behind a stake address whose output had to be created below a cutoff one full epoch before the beacon height (§7.1), and r_h is the one draw secret that horizon root fixes for the height. The key is inside the hash and in every leaf under the horizon root, so a draw secret copied from another miner's header fails under the copier's own stake address and never carries the victim's score (§4.7). A genuine tie between two distinct keys has probability about 2^−255; the tie-break (highest score, then lowest public key, then lowest merkle root) makes the outcome deterministic and offers nothing to grind.

A node checks a received header in six stages, cheapest first, and a header stops at the first stage it fails:

  1. Sender and shape. The sender is not banned, the header is exactly 743 bytes, and its version is valid.
  2. Cheap claims. The height's segment lies inside the horizon the header names (two integer compares, no hashing), and the claimed score, one hash over the header's key and draw secret, could enter the slot's top five. A header that fails either is dropped before any expensive check and is not relayed.
  3. Admission bounds. Verification slots are limited, so stages 4 to 6 run only when there is room: the same header is not already being verified, the node has fewer than 64 headers in verification, and the sender has fewer than 16 of them. A header refused here is not judged invalid and its sender is not penalised. It is parked, and taken up again, counted against that peer's share, when another peer relays the same header, so one busy or flooding sender cannot keep a valid header from being judged.
  4. Signature and draw secret. On the validation pool: the SQIsign signature, then the walk from the draw secret up to the horizon root.
  5. Slot and chain. The miner has not been cancelled for equivocation on this attempt (§4.6), the header is classified against the node's clock (current, early or ahead of it), and its parent is known or within the fork window.
  6. Candidacy. The election seed must follow from the parent's, and the stake address rebuilt from the derived root must hold an eligible output (§7).

A received header enters the ranking only after all six stages pass. Stage 2 judges only the score the header claims, so the expensive checks of stages 4 to 6 must confirm it before it can displace an entry already ranked. The one header that skips these stages is the node's own: it is ranked when mined, after the miner's own eligibility check (§4.5). A junk header with a made-up draw secret costs at most one signature check, one walk and one bounded stake lookup, whether or not its sender holds stake. With top-5 relay a node verifies about 5·(1 + ln(N/5)) headers per slot for N miners: about 31 at a thousand miners, 66 at a million.

4.4 The election seed chain#

The header carries two hash chains with different jobs. prev_block is the identity chain: the BLAKE3 hash of the parent's signed fields. It leaves the signature out, because SQIsign signing is probabilistic (one message has many valid signatures) and anyone holding one signature can derive another valid one over the same bytes. election_seed is the beacon chain:

election_seed(h) = BLAKE3("spek/election-seed/v2" ‖ election_seed(h−1) ‖ miner_pubkey ‖ r_h)
election_seed(0) = 0x00…00

The seed binds only the parent's seed, the winner's key and its committed draw secret. No signature, merkle root or header hash enters it, so re-signing or re-ordering a block cannot move any later beacon.

4.5 Mining a block#

A miner makes at most one attempt per slot. At the slot boundary it reads the parent block, the parent's election seed, the epoch beacon and the stake ledger from one consistent chain state, then works in three steps.

Decide whether to take part.

  1. Check that it is in sync: its tip must be the previous slot (chain_height + 1 == current_slot). A node behind the clock would sign a block at the wrong height, so it skips the slot. This is not a pause during block download, which the protocol forbids (§12.2).
  2. Pick its eligible horizon (in the launch phase, the one whose stake program holds the round's ticket record).
  3. Check its own eligibility with the same rule block validation uses, and skip the slot rather than produce a block every peer would reject.

Draw and build.

  1. Compute the draw secret r_h and its Merkle path, then the score and the next election seed.
  2. Build a block from the mempool and check it: structure, locktime, genesis spend rules, size and count limits, merkle root.

Sign and publish.

  1. Sign the first 543 bytes of the header with SQIsign.
  2. Save the signed attempt to disk, so a restart within the slot re-announces the same header instead of a second, different one (§4.6).
  3. Broadcast the header. The full block is sent only to peers that ask for it, after the ranking is known (§3.2).

4.6 Equivocation#

Each node keeps only one entry per miner key per parent per slot. Because the block hash leaves the signature out, a second header with identical signed content is the same block, and the two are merged. A second header with different signed content for the same attempt is equivocation: the miner's entry is removed, the attempt is cancelled for the slot under its attempt-identity hash BLAKE3(prev_block ‖ miner_pubkey) on every node, and a compact proof is gossiped so every node reaches the same verdict.

4.7 What the election guarantees#

Together, §4.1–§4.6 and the eligibility rules of §7 give the election these properties:

  • The same draw on every nearby fork. Two chains that share every block up to an epoch's beacon height give each key the same score at each height of that epoch. Every fork the network resolves near the tip shares that history. A branch that forks below a beacon height does not: from its first 1,441 blocks on, a private branch reads its own beacons (§17).
  • A seed no miner can steer, except by withholding. The election seed, and every beacon read from it, depends only on the previous election seed, the winner's key and the winner's committed draw secret. A miner can change nothing else in its block that moves them. Its one lever is to withhold blocks, and only withholding at the end of a beacon's source epoch is an informed choice, worth 0.3–0.6% of its own wins averaged over all epochs (§4.2).
  • Inputs fixed before the beacon. A stake output or ticket record counts only if it was created a full epoch before the beacon height, so a key and its horizon root are fixed before the randomness they are drawn against exists. A ticket is found off chain, but it is created, for this rule, when its record lands in a block (§7.2).
  • One value per height. For each stake address and height exactly one draw secret verifies (§4.8), so there is nothing to try again.
  • One draw per stake address and horizon. Each eligible header names one horizon and one output at its stake address holding a full stake unit, so at consensus draws scale with funded stake addresses, not with keys (§7.1). The draw secret root belongs to a key file, not to a key, and verifiers cannot tell which root built a horizon. A key whose horizons were built from different roots therefore holds an independent draw for each funded horizon; it publishes only its best header, so the network sees one header and no equivocation (§4.6). The reference node does not do this out of the box: it runs one key file (one root), builds every horizon of the key from it, and so its horizons reveal the same r_h at a height and give that key one draw per slot. Several draws from one key need a modified node that holds several roots for it; several draws from the reference node need several keys.
  • Draws bound to the key. The key is inside both the score and every leaf under the horizon root. A copied horizon root is invalid under any other key. A draw secret copied from a published header walks up to the victim's segment top, so under the copier's own horizon it rebuilds an address that holds nothing and the header fails like any wrong draw secret. It verifies only under an address whose horizon root the copier built from the victim's revealed segment tops and funded before the beacon. That address is a stake unit of its own: it pays the full requirement, it has at most the one draw any funded address has (§4.8), its score is drawn under the copier's key and is unrelated to the victim's, and it draws only in slots where the victim publishes, for the rest of a segment whose top the victim had already revealed. Copying draw secrets therefore buys no draw that an own horizon on the same stake would not give.
  • Draw secrets independent of the signing key. The draw secret root is separate random bytes, so recovering a SQIsign secret key reveals no future draw secret.
  • No guessed beacons. Every score is computed with a beacon read from the chain being scored (§6.1); a header whose beacon cannot be read yet is held aside, never scored with a guess.

4.8 Why only one draw secret verifies#

The election rests on one property: for a given stake address and height, exactly one draw secret verifies. If a miner could produce two, it would score both and publish the better one, a retry the election is built to rule out. The argument below is a sketch, not a proof, and no cryptographer has reviewed it (§17).

The claim, precisely. Fix a stake address, built from a key pk, a horizon root C and a horizon start J0, and a height h. Then any party, including the address's owner, who produces two different draw secrets that both verify for that address and height has found a collision in BLAKE3. The claim is about one stake address. A key can hold several funded stake addresses, and each gives its own draw (§4.7, §7.1); that is the one-draw-per-stake-unit rule, not a retry.

The setting. A stake address is hidden-key address of (pk, BLAKE3("spek/slot-commit/v1" ‖ C ‖ J0)) (§7.1). It holds stake only if an output was created there before the stake cutoff, so pk, C and J0 are fixed before the beacon that decides the scores exists. For a height h the verifier then has nothing to choose:

  • the segment g = ⌊h / S⌋ and the offset o = h mod S follow from h;
  • the leaf index j = g − J0 follows from h and J0, and must lie in 0 … 1023;
  • the walk has a fixed shape: step r_h exactly o + 1 times, step(x) = BLAKE3("spek/slot-step/v1" ‖ x), to reach a segment top T; hash the leaf BLAKE3("spek/slot-leaf/v1" ‖ pk ‖ T); then hash exactly 10 times up the tree with the path, each node BLAKE3("spek/slot-node/v1" ‖ left ‖ right), left or right as the bits of j dictate. The root the walk ends at, with J0 and pk, rebuilds the stake address, which must be the funded one.

The argument. Suppose two different draw secrets r ≠ r', with paths P and P', both verify for the same stake address at the same height. Compare the two walks from the top down.

  1. Address. Both rebuild the same address from the same pk. If they reached it through different roots (C ≠ C'), the commitment hash BLAKE3("spek/slot-commit/v1" ‖ C ‖ J0) or the hidden-key address over it has two inputs with one output: a collision. So both walks end at the same C.
  2. Tree. If the walks differ anywhere in the 10 tree levels, there is a highest level where the two parents are equal but the inputs differ: two different 81-byte inputs to the node hash with one output, a collision.
  3. Leaf. If the tree levels agree but the segment tops differ (T ≠ T'), the leaves are equal with different inputs: a collision in the leaf hash.
  4. Chain. If the tops agree (T = T'), then r and r' each reach T in exactly o + 1 steps. They start apart and end together, so some step takes two different inputs to one output: a collision in the step hash.

Every case ends in a BLAKE3 collision, so producing two verifying draw secrets is at least as hard as finding one.

Why each piece is needed.

  • Fixed positions. The number of steps is set by the height, the tree depth is fixed at 10, and the leaf index is set by J0, which is inside the stake address. A verifier never lets the prover choose where in a chain or a tree its value sits, so each case above compares two walks of the same shape. Naming another J0 names another stake address, with its own stake.
  • Domain tags. Steps, leaves, tree nodes and the commitment hash use different tags and input lengths (49, 132, 81 and 55 bytes), so no value can be read as a different kind of hash in a second walk.
  • The key in every leaf. A leaf contains pk, so a horizon root built under one key gives no verifying draw secret under another (§4.7).
  • A dishonest owner. The argument never assumes C was built honestly. An owner may fill its tree with anything, but once the stake output commits C before the beacon, it can open each position one way only, unless it finds a collision.

What this does not cover. The sketch shows binding: a committed horizon opens one way per height. The election also needs hiding: nobody but the owner can compute r_h before it is published. That rests on different assumptions: the draw secret root is secret (§4.1), and each step is hard to invert, so a published r_h and the tops reveal nothing about the values below them that later heights use. It is not argued here.

Why this matters. X-VRF, a related hash-based construction proposed for proof-of-stake election, was broken on exactly this property (reference 5). As we read that break, X-VRF's verifier did not pin which one-time key in its tree answered a given input, so a key holder could answer one input from several positions and choose among the outputs. In Spek the position is pinned twice: by the height (the number of steps and the leaf index) and by J0, which is inside the funded stake address. The assumption is collision resistance alone. BLAKE3's 256-bit output gives about 2^128 work against a classical attacker. Against a quantum attacker the generic Brassard–Høyer–Tapp bound is about 2^85, and it needs a quantum memory of a similar size, so it is a bound, not a practical attack estimate.

5. Slot settlement and the null block#

At the slot boundary, each node goes through its retained candidates in rank order (up to the top five peer headers, plus its own header if it mined one, which counts only while it ranks within the top five; peers keep only their own top five, so an own block ranked sixth is one no other node holds) and commits the first whose full body is in hand and passes full validation. Holding five candidates while fetching three leaves backups for a top candidate that is invalid or whose body never arrives. A node validates the rank-1 body as soon as it arrives, so the verdict is normally ready well before the boundary. If it is still being computed, the node waits a bounded time for it, because committing a lower rank while the verdict computes would put the node on a different block from its peers. The wait always ends well before the next boundary. While a node waits, the next slot is already open; its own header for that slot goes out once it commits, still inside the block phase, where late headers enter the ranking (§3.2), so a held node competes late rather than not at all.

A Level V signature costs up to 6.119 times a Level I one to verify, but Level V witness bytes are weighted by ρ (the Level V witness weight, §9.4) in virtual size, so a block of ordinary spends takes no longer to verify, however many Level V inputs it holds, than a full block of ordinary Level I spends. Script leaves written to maximise signature checks can push that to about 1.27 times, the most the per-input signature budget allows (§9.3).

If a slot closes with no committable candidate, every node builds the canonical null block for (height, prev_block): version 1, all-zero miner key, signature and slot fields, zero merkle root, no transactions and no coinbase. Its election seed is derived by the normal rule with a fixed null identity and an all-zero draw secret, so the beacon chain continues unbroken. It is built, not mined, so nothing crosses the network. Its score is 0, below the minimum real score of 1, so any real block for that height outranks it: if a late winner surfaces, fork choice replaces the null, with no ban and no penalty. Fork choice compares two branches once each holds two blocks above the fork point (§6.2), so the usual case rolls back two blocks: the null and the block built on it. A node that settles several nulls in a row on a branch the rest of the network left rolls back more. Null blocks mint nothing and are stored and served like ordinary blocks.

6. Chain selection and confirmation#

6.1 Chain weight#

d(b)         = 2^255 − score(b) + 1                  // how far b's score fell short of the maximum, 1 … 2^255
work(b)      = 1 + 2^32 · log2(2^255 / d(b))         // a real block: 1 … 1 + 255·2^32; a null block: 0
chainwork(b) = chainwork(parent(b)) + work(b)        // score(b) uses the beacon of b's epoch, read from b's own chain

The score still decides each slot: the highest score wins (§4.3). Fork choice sums a block's work, the logarithm of how close its score came to the maximum, in fixed point with 32 fractional bits. Nodes compute it in integers only (spek_core::block_work), so every node gets the same value. Chainwork is an arbitrary-precision sum that is never truncated or reset.

Why the work is summed. Every height has exactly one block, a null block where no candidate arrives, so two chains over the same heights have the same number of terms and their sums differ only in the work. Each slot's best score comes from the draws in play for it, so a chain backed by a larger share of the draws collects more work per slot in expectation (Appendix B), and the heavier chain is the one more draws stand behind. A null block has work 0 and every real block at least 1, so a chain that settled a slot with a null weighs less than one that settled it with any real block, which is why a late real block replaces a null by a short reorganisation (§5).

Why the logarithm. With N draws a slot's best score falls short of the maximum by about 2^255/N, and two branches' best scores differ by a similar amount. A sum of raw scores would therefore count one null, which falls short by the whole 2^255, as much as N slots of ordinary differences. An attacker could exploit that: in slots where it holds the five best headers (about q⁵ of slots) it withholds their bodies, so the honest chain settles nulls, while it keeps those blocks on a private branch. Under raw scores that branch gained on the honest chain from about q = 0.30 at 1,000 draws, 0.20 at 10,000 and 0.13 at 100,000. Under work a null costs a chain only about log2 N units against an ordinary per-slot difference of log2((1−q)/q), so forcing nulls pays only from about q = 0.46 at 1,000 draws, 0.45 at 100,000 and 0.44 at 10 million (reference 10), the range where a private branch already breaks even (§17). The cost is that work weighs a slot's evidence less efficiently than raw scores do, so a given confirmation depth protects against a little less (Appendix B).

A block's score depends on the beacon of its epoch, and every chain derives its beacons from its own election seed, so a node scores each block with the beacon of the chain that block sits on. If that beacon cannot be read yet, the header is held aside and never scored with a guess.

  • Live headers are scored with the main chain's beacons. A header for an epoch other than the current or the next one is held aside, never ranked.
  • Forks near the tip are at most 5 blocks deep, far less than an epoch, so the block their beacon comes from is always shared with the main chain.
  • Candidate chains in download read each epoch's beacon from their own headers once they fork below that epoch's beacon height. Until that header has arrived, the candidate's weight is unknown, and a node never switches to a chain of unknown weight.

6.2 Fork resolution#

  1. Forks near the tip. When a competing branch forks within the fork window (PROPAGATION_FORK_WINDOW = 4 blocks below the tip), the two branches are compared by chainwork once each holds at least two blocks above the fork point; the heavier wins and the other is dropped. Waiting for both sides avoids switching back and forth on every block. The reorganisation is checked against a copy of the ledger before any live state changes, so an invalid fork block leaves the chain untouched. Rollback on this path is bounded at 5 blocks, one more than the window, because the main chain can advance by a block while the resolution is in flight.
  2. Deeper forks. If no common ancestor lies inside the window while the peer's chain keeps pace with the clock (which is what both sides of a healed network partition look like, since both mine every slot), the node switches to a full download, finds the true branch point, compares chainwork above it, counting only blocks whose stake existed at the branch point (§12.1), and reorganises at any depth above its restoration pin.
  3. Checkpoint barrier. A fork whose branch point lies behind the node's restoration pin or a hard checkpoint is never resolved automatically, and the peer offering it is banned. Checkpoints sit on a 4,000-block grid (about 33 h), and the restoration pin is the newest grid boundary buried at least one full interval below the tip, so it trails the tip by 33–67 h. Only a partition that outlasts a boundary by more than an interval leaves the two sides with different pins; that state needs operator recovery.

Coinbase outputs mature after 3,000 blocks (about 25 h).

6.3 Confirmations, pins and checkpoints#

Three layers protect a transaction once it is in a block:

  • Confirmations (probabilistic). Draws are fixed per height, so an attacker can rewrite history only by out-weighing the honest chain over the same heights. Appendix B gives, first, the probability that a transaction at k confirmations is ever reversed and, second, the confirmations needed for under one reversible slot per century against an attacker holding share q of the draws who may choose its fork point in hindsight: 59 confirmations (30 min) at 20%, 223 (1.9 h) at 33%, 679 (5.7 h) at 40%. Integrators choose their depth from the share they want to tolerate.
  • Restoration pins (per node). A running node never reorganises below its pin, which trails the tip by 33–67 h.
  • Checkpoints (weak subjectivity). A node with no history of its own trusts the checkpoints compiled into its release and pin files signed by a threshold of checkpoint signers (§12.3).

There is no finality gadget and no rollback limit shorter than the pin.

7. Eligibility: ticket records and stake outputs#

No election rule over independent draws can stop one party from fielding many draws, so the cost of fielding a draw is where Spek's security lives. That cost has two phases, and in both the thing that makes a key eligible must be on chain before the beacon it competes against.

7.1 After the launch phase: one stake output#

min_coin_requirement(h) = max(0.8 × block_reward(h), 0.1 coin)     for h ≥ 129,600
stake_address           = hidden-key address of (pk, BLAKE3("spek/slot-commit/v1" ‖ C ‖ J0))
stake_cutoff(h)         = beacon_height(epoch(h)) − L

A header at height h is eligible only if its horizon covers h and its stake address, rebuilt from the header's key and the root its draw secret derives, holds one unspent output that:

  • is worth at least the requirement (several smaller outputs do not add up);
  • was created at a height below stake_cutoff(h) (creation height < stake_cutoff(h)), one full epoch below the beacon height, so new stake first counts about 24–36 h after it is created;
  • if it is a coinbase output, is mature.

Eligibility is judged against the parent block's ledger, so spending the stake output ends eligibility from the next block, and on a fork each branch's own ledger decides. Counting one output per draw keeps the check to a short walk of a value-ordered index: every output it steps over holds at least a full requirement, so filling a stake address with dust cannot slow anyone's check. A stake address belongs to exactly one horizon, so each funded horizon is its own address with its own output and its own draw per slot. At consensus a key with two funded horizons holds two draws, which costs two requirements, economically the same as two keys: one output counts for one address only, and moving coins between addresses restarts their aging. The reference node builds every horizon of a key from one draw secret root, so its two horizons reveal the same draw secret at a height: during a renewal overlap it holds two funded stake units but one draw (§4.7).

Why these numbers. The requirement is 80% of a block reward so that a single win more than pays for one stake output: a winner funds its next horizon from its coinbase, and the requirement stays below a block's own reward until the floor binds. The 0.1-coin floor stops it falling to dust as the reward halves; it is also the smallest value the node's stake index holds, so dust never enters the eligibility lookup. The 24–36 h age is not a tuned delay: an output must have been created below a cutoff one epoch (12 h) under the beacon height, and the beacon height is itself one epoch before the epoch it serves, so new stake reaches its first draw after between 2L+2 and 3L+1 blocks.

After the launch phase, block production is capital-proportional: a holder of X coins can fund ⌊X/requirement⌋ stake outputs and wins slots in that proportion. The requirement sets the size of one draw, not the cost of an attack: matching the honest network costs roughly the capital it holds, whatever one draw costs. The requirement halves with the reward, and the 0.1-coin floor only binds from the ninth halving (about 36 years) out. From then on the reward (about 0.098 coin at the ninth halving) is smaller than the requirement, so one win no longer pays for a stake output.

The stake key is public in every header its miner publishes and lives on the mining machine, so the node keeps exposure to one stake unit. By node policy (not consensus), the coinbase pays the stake address of the first horizon not yet funded, then a separate hidden-key payout address. A winner therefore funds its next horizon for free (renewal is described below). The node also merges a stake address funded in pieces into a single output.

Renewal is a transaction. A miner that never wins keeps its eligibility by funding the next horizon's address with an ordinary transaction, at least one requirement, created early enough to age. The node builds the next horizon about a year ahead, and funds it itself from any surplus beyond the counted output at the current address; a node holding exactly one requirement needs a transfer from a wallet. Nothing is locked, so once the new horizon is in force the old output can be spent. The second requirement is held from the moment the next horizon is funded, which by default is a year before the old one ends (the lead is an operator setting); a shorter lead lowers it, but must stay above the 24–36 h an output needs to age. A miner that wins a block gets the next horizon funded by its coinbase.

This also avoids the classic proof-of-work death spiral. Honest operating cost is close to zero, so a falling price gives no miner a reason to switch off, and the honest draw count does not collapse with the price. Price exposure sits on the attacker's side: buying a large share drives the price up as it buys, and the stake it holds loses value when the attack is seen.

7.2 Launch phase: RandomX ticket records#

At launch nobody holds coins, so a coin requirement would be zero and a draw would cost one SQIsign key generation (sub-second, parallel, pre-computable). The first 45 days (129,600 blocks) therefore use a different price. The launch phase is divided into 15 rounds of W = 8,640 blocks (3 days). A ticket is a nonce such that

RandomX_K( "SPEK-TICKET-V2" ‖ round ‖ round_hash ‖ A ‖ nonce ) < D,   D = 2^228
A            = the stake program (the 32-byte hidden-key program of the miner's stake address)
K            = genesis hash (fixed for the whole launch phase)
round_hash_0 = genesis hash
round_hash_1 = hash of the block at height W/2
round_hash_r = hash of the block at height (r−1)·W          for r ≥ 2

A ticket counts only once it is recorded on chain: a 48-byte record ("SKTR" ‖ round ‖ A ‖ nonce) carried as a zero-value OP_RETURN output in a launch-phase coinbase, at most 16 per block, one per (A, round) on the chain, each for the current or the next round. A block with an invalid record is invalid, and after the launch phase a coinbase may carry none. Records travel on their own gossip topic and wait in a bounded pool; every miner includes pending ones. A record counts for an epoch only if it landed below that epoch's stake cutoff, so to cover a whole round it must land about two epochs before the round starts. That leaves a 48-hour search window for rounds 2 and later, whose hash is fixed a full round ahead, and about 12 hours for round 1, whose hash comes from the middle of round 0. The genesis coinbase is not bound by the 16-record limit; it carries the open launch's records (below). Because the ticket is committed before the beacon it competes against exists, a miner cannot rank free keys by their scores in an already-known epoch and buy tickets only for the best ones.

The RandomX instance is a Spek variant with its own parameters, so rented hash power built for other chains cannot be pointed at it. Verification runs in light mode (15–30 ms, 256 MiB cache); searching uses the dataset of about 2 GiB. D was set so that a 2018-era 8-core desktop's spare cycles yield about three tickets per round; a slot in which no ticket holder is eligible gets the null block.

A round's hash is read from the candidate chain's own ancestry, so a ticket's validity depends only on the block and its chain, and re-checks identically during download. Round 1 is keyed by the block in the middle of round 0 rather than by genesis, so a pre-launch search can buy at most one round of tickets, not two.

Open launch. Epochs 0–2 (the first 36 hours) count only records written into the genesis coinbase, and anyone can win one:

  1. Open. The search opens at a pre-announced Bitcoin block. Its hash, with the network name, gives the launch key K_L, so no ticket can exist before it.
  2. Search and submit. Anyone searches for a round-0 ticket under K_L (the same target D, with K_L as the RandomX key and round hash) and submits the record to a public submission channel. The channel checks each ticket on arrival and lists every valid entry with its ticket hash, so anyone can recheck the listing.
  3. Seal. After the deadline the organiser publishes the sealed list with the genesis timestamp (6 hours after the deadline), the genesis message and the allocation, a digest over all of them, and the height of a Bitcoin block six blocks past the tip at that moment. Independent witnesses (anyone may witness) record the digest before that block is mined.
  4. Select. The genesis takes up to 1,970 records (a transaction may have at most 2,000 outputs, and the 30 allocation outputs come first), one per key, lowest ticket hash first, so when more are submitted than fit, searching longer buys better odds.
  5. Derive. The launch nonce is derived from the launch key, the seal digest and that Bitcoin block's hash, and the genesis builder is deterministic. The launch beacons therefore depend on a value nobody knew while any input could still change, and anyone can recompute the selection and the genesis block from public inputs.

One record is one key, and a node mines one key, so a launch seat costs what every later round costs: one ticket.

Launch-phase draws are therefore priced by sustained work per round rather than one-time key generation: a bank of keys is worthless without fresh work per key per round, and a flood of keys fades within two rounds once its operator stops paying for it. Ticket holders must fund a stake output below the cutoff of the first epoch after the launch phase; the node warns seven days ahead.

7.3 What the schedule does and does not do#

Both phases award blocks in proportion to the draws held. After the launch phase, draws are bought with coins that (apart from trading) only block rewards create, so the distribution of coin shares at the end of the launch phase carries forward under the election. Shares change afterwards only when coins change hands. One key per node is client policy, not consensus: nothing ties a miner key to a machine, and the economics do not depend on it.

How the first stake outputs form. Coins exist only as block rewards and the disclosed genesis allocation. By the end of the launch phase the chain has minted 6,480,000 coins in rewards (129,600 blocks at 50 coins), all paid to launch-phase winners, plus 2,175,000 coins of the allocation that are spendable from coinbase maturity: the founders' opening tranche (675,000) and the stewardship fund's opening tranche (1,500,000) (§10.2). The requirement is 40 coins, so rewards alone can fund at most 162,000 stake outputs, and a key that never won a launch-phase block holds no coins and becomes eligible later only by buying them. The first post-launch eligible set is therefore the launch winners that funded an output below the first cutoff, plus holders of allocation coins and buyers. What the election inherits is the coin distribution at the end of the launch phase, not the ticket count.

What a ticket costs. A ticket is a RandomX hash below 2^228, which takes 2^28 (about 268 million) evaluations on average, and the target is set so that a 2018-era 8-core desktop finds about 3 tickets per 3-day round: roughly one ticket per desktop-day. A ticket counts for one round, one key and one stake address, so a draw in every round costs a fresh ticket in every round. With H honest tickets in a round, an attacker needs H·q/(1−q) tickets to hold a share q of the draws (about H desktop-days for half) and pays that again in each of the 15 rounds. This is an estimate in desktop-days, not a price: it assumes Spek's RandomX parameters give no hardware an edge over an ordinary CPU, which is a design goal rather than a measurement of any attacker's equipment, and it does not bound an attacker who rents far more compute than the honest network holds.

8. Cryptography#

8.1 Signatures: SQIsign Level I and Level V#

Every signature in the system is SQIsign (isogeny-based), produced by a vendored reference implementation behind an FFI boundary. Timings below are given for two arithmetic backends: ADX, the faster one for recent x86 processors, and portable, the plain C fallback. There is no ECDSA, no Schnorr, and no elliptic-curve library linked into the signature code, and a test on the dependency graph keeps it that way.

Level Target Public key Signature Secret key Verify (ADX / portable) Used for
I NIST level 1 83 B 200 B 270 B 2.68 / 5.03 ms Headers, mining keys, stake outputs, everyday outputs (the default)
V NIST level 5 169 B 406 B 549 B 16.4 / 26.7 ms Opt-in custody outputs; every genesis allocation, council and guardian key

Signing a Level I header takes 25–40 ms, once per slot for a miner; the signer verifies its own signature before releasing it. ADX is the faster arithmetic backend on recent x86 processors; portable is the plain C fallback.

If Level I is broken. In the worst case an attacker who can forge Level I signatures can (1) spend the stake output of any key whose public key appears in a published header, which is one stake unit per key (§7.1); (2) forge the signature on a header for a past height whose r_h was already revealed, and so build a branch from any point where that key held stake, as far back as the restoration pin for a running node or the compiled checkpoint for a fresh one (§12.3); and (3) copy a just-revealed r_h into a second header to force the slot to be cancelled as equivocation, a liveness attack, not a theft. It still could not win a live slot as someone else, because it would also need that key's unrevealed r_h, which comes from an independent draw secret root and is protected only by BLAKE3, and it could not touch outputs whose key is still hidden behind a hash. Mining keys rotate with every horizon, so moving headers to a new level later is a hard fork that phases in as horizons expire, with no coin moves.

Standardisation and review status. SQIsign is not a NIST standard. NIST advanced nine candidates to Round 3 of its additional digital-signature process in May 2026; one of them, HAWK, has since been withdrawn by its submission team, leaving eight, and SQIsign is among them. That round is expected to last about two years, a draft standard could not appear before about 2028, and SQIsign may be dropped. "Level I" and "Level V" refer to the security categories the parameters target (comparable to AES-128 and AES-256 key search), not to any NIST approval. Spek uses SQIsign rather than the standardised ML-DSA for its size: a 200-byte signature and an 83-byte key against roughly 2.4 KB and 1.3 KB. The trade-off is that SQIsign's security rests on a younger assumption (the supersingular endomorphism-ring problem) with less cryptanalytic history than lattices, and on a reference implementation that was not built for production. Spek's copy of that implementation and its Rust FFI boundary have been reviewed only by AI models (Claude). No cryptographer, SQIsign author, or independent human auditor has reviewed them before launch.

A public key has exactly one valid encoding: every field element must be canonical (below the field prime), and the starting curve E₀, whose endomorphism ring is public, is never an acceptable key. A non-canonical encoding is a decode error, never silently corrected. A verification cache (262,144 entries) remembers only valid signatures, so re-presented valid signatures cost a hash lookup; it never caches failures and never changes a verdict.

8.2 Hashing: BLAKE3#

BLAKE3 is used for block hashes, election seeds, beacons, scores, draw secrets and their Merkle trees, transaction merkle trees, script and hidden-key commitments, the OP_BLAKE3 opcode, addresses, and the UTXO script index. Every consensus hash is domain-separated by a tag string. Transaction merkle trees tag leaves (0x00) and interior nodes (0x01) so no byte string can be valid as both; odd levels duplicate the last node, and a block may not contain the same transaction id twice.

8.4 Hidden keys and script commitments instead of Taproot#

Taproot hides a script tree by tweaking an elliptic-curve key. Isogeny keys cannot be tweaked that way, so Spek's analogue, ScriptCommit, commits to the script tree with a hash:

commitment = BLAKE3(T ‖ T ‖ pubkey ‖ script_merkle_root),  T = BLAKE3("SpekScriptCommit")
key-path-only outputs use commitment = 0x00…00

The default output hides even the key. A hashed output is 34 bytes, a witness version and a 32-byte program, the same shape as a Bitcoin P2WSH or P2TR output:

v1 (Level I):  OP_1 <32 B>   program = TH("SpekHashedCommit",   pubkey83  ‖ commitment)
v2 (Level V):  OP_2 <32 B>   program = TH("SpekHashedCommitL5", pubkey169 ‖ commitment)

A key-path spend reveals the key and commitment next to one signature. A script-path spend reveals the leaf, its merkle proof and a control block; the node recomputes the commitment and the program before running the leaf in the script machine (§9.3). Leaves under a v2 output verify Level V signatures. Multisig, timelocks, hash locks and atomic swaps can be expressed; key aggregation cannot. The plain ScriptCommit output (OP_1 <83-byte pubkey> <32-byte commitment>, 118 bytes) remains valid for outputs that want the key visible.

Addresses are Bech32m with the prefix spek: witness version 1 carries a 32-byte hashed program or the 115-byte plain program, and version 2 a 32-byte Level V program. Decoding re-encodes and requires a byte-exact match, so each output script has exactly one lowercase address string. Wallets use the hashed form for every receive, change and coinbase address, so a public key is exposed only when its output is spent. The exception is a stake key, which every header it signs makes public.

8.5 Crypto-agility#

There is no per-transaction choice of algorithm and no runtime negotiation: at any height exactly one scheme is valid for a given output form or header version, which rules out downgrade and algorithm-confusion attacks. The witness version selects the output scheme (1 = Level I, 2 = Level V; versions 3–16 are reserved), and the header version selects the header scheme, activated through the height-indexed upgrade schedule (§14). Because the signed message commits to every spent output's locking script, a signature for one scheme can never be reinterpreted under another. A hash-committed output is the shape other chains are adding for a post-quantum migration; Spek starts with it, and with a second, larger parameter set already live for custody.

9. Transactions and scripts#

9.1 Model#

Spek is a UTXO ledger: coins are unspent outputs of earlier transactions, as in Bitcoin. Values are unsigned 64-bit integers counted in bits (10⁸ bits per coin); there is no floating point anywhere in the protocol or its RPC. Exactly four output forms can be created: hashed Level I (34 bytes), hashed Level V (34 bytes), plain ScriptCommit (118 bytes), and zero-value OP_RETURN data outputs, which never enter the UTXO set. There is no pay-to-pubkey form. Everything else is rejected, in blocks and in the mempool, because an unspendable output would burn its coins forever.

The transaction id is the BLAKE3 hash of every field except the witnesses (the signatures and revealed data), so it is fixed before signing and no relay can change it; the block merkle tree commits to a second hash over the full encoding, witnesses included. The signed message commits to the chain (its genesis block hash), the inputs, the outputs, every spent output's value and locking script, and the transaction version, but not to the witness. Committing to the chain matters for offline signers: the same keys produce byte-identical scripts on every chain, so without it a signature made on a test chain could be valid on mainnet. The transaction id leaves the witness out, but the block's merkle root commits to it, so the full encoding of a spend is fixed only while its witness is the only one that satisfies it. Validation therefore enforces a full canonical form (SQIsign signatures themselves stay malleable, §15): canonical witness encoding, minimal numbers, a clean stack, minimal conditionals, and one signature rule under which a non-empty signature that fails verification aborts the script rather than evaluating to false. Every signature signs the whole transaction (SIGHASH_ALL); there are no other signature modes.

9.2 Time locks#

All locks are block-height locks; there is no timestamp variant, because height is time. Absolute nLockTime, relative nSequence locks (as in Bitcoin's BIP68, version 2 and up), OP_CHECKLOCKTIMEVERIFY and OP_CHECKSEQUENCEVERIFY are enforced with one spending-height rule shared by block validation and the mempool: the height the transaction would be mined at.

9.3 Script machine#

A minimal stack machine runs ScriptCommit leaves: 82 opcodes, frozen per leaf version (0xc0). OP_BLAKE3 takes the byte Bitcoin uses for OP_SHA256 (0xa8), so a Bitcoin script does not carry over byte for byte. SHA-256 is still available as OP_SHA256 at 0xbb, so a cross-chain atomic swap can lock both sides with the same SHA-256 hash: the secret that claims one side opens the other. OP_CHECKSIG, CHECKSIGVERIFY and CHECKSIGADD verify SQIsign at the level of the output's witness version; Bitcoin's CHECKMULTISIG opcodes are disabled. Limits: 10,000-byte scripts, 1,000-item stacks, 520-byte elements, 100-deep conditionals, 128-deep merkle proofs. Signature verification is the dominant cost and a failed signature cannot be cached, so each input carries a signature budget (283 witness bytes per Level I verification and 575 per Level V verification, the size of one signature plus its public key, charged before the verification): an attacker-written leaf cannot make a node do more than about one verification per genuine signature's worth of witness bytes. Everything else a script can do costs under 2 ms per input at the limits.

9.4 Virtual size, fees and the mempool#

A Level V verification costs up to 6.119 times a Level I verification, so each Level V input's witness bytes count ρ = 151/50 = 3.02 times in a transaction's virtual size. ρ comes from two measured numbers: the largest Level V to Level I verification ratio across both signature backends (6.119: ADX 6.12, portable 5.29; each ratio compares Level V and Level I measured the same way, warm cache to warm and cold to cold, so the table in §8.1, which mixes a warm Level I time with a cold Level V time, gives a slightly different 5.31), divided by how much larger a Level V signature and key are (575 bytes against 283, 2.03 times), which gives 3.01, rounded up to 3.02. Blocks are limited to header + Σ vsize ≤ 2 MiB, and every fee rate is measured in virtual size, so Level V inputs cannot make a block slower to verify than a full block of ordinary Level I spends; script leaves written to maximise signature checks can reach about 1.27 times that (§5, §9.3). For a transaction with no Level V input, virtual size equals its size in bytes.

A relay fee floor (250,000 bits at launch, falling each halving era) is flat for transactions up to 3,000 virtual bytes and rises linearly above that, so occupying the UTXO set permanently is priced while ordinary payments are not. The mempool is bounded (200 MB and 100,000 transactions by default). Block templates fill 85% of a block by fee rate and the rest oldest-first, and a miner's coinbase claims the block reward plus fees, never more. One transaction type sits outside the fee market: a guardian's cancellation of a staged allocation spend (§10.2) cannot raise its own fee, so the mempool admits it without a fee contest, never evicts it, moves it to the front once its deadline is within a day, and lets nothing but another cancellation replace it. A flood of higher-paying traffic therefore cannot run out the 30-day veto window.

11. Network protocol#

11.1 Transport and peers#

Spek runs on libp2p over QUIC only (encrypted with TLS 1.3, with stream multiplexing). Hosts on networks that block UDP cannot take part. Peers are found from a built-in bootstrap list, DNS seeds and a Kademlia random walk. Bootstrap nodes and DNS seeds only help a node join: at most half of a node's outbound connections come from DNS answers, and a synced node lets go of bootstrap nodes and does not redial them, so they keep room for nodes that are still joining. Every connection, however it was found, must pass diversity limits on IP address, network group and hosting provider, so one operator cannot cheaply fill a node's peer table. Native IPv6 is not supported at launch.

11.2 Propagation#

Headers flood the network and are verified away from the event loop on a priority validation pool (signature 2.7–5.0 ms plus the draw secret's walk to its horizon root), with per-peer limits on work in flight, after the one-hash claimed-score filter has dropped any header that could not rank. Block bodies are pulled on request, never pushed. Launch-phase ticket records travel on their own topic and are checked at mempool priority, never on the slot-critical path.

Current-slot blocks are fetched compact-first: the serving peer sends short transaction ids keyed by a nonce it chooses, the receiving node rebuilds the block from its mempool and must arrive at the header's merkle root, and any failure falls back to requesting the full block. Full blocks remain the unconditional fallback and the path for initial download.

The scheduler serves the current slot's rank-1 block validation ahead of everything else: it has a reserved lane, then live propagation and catch-up share the next priority, then initial download, then mempool admission.

11.3 Misbehaviour#

Violations are counted per IP address in three classes (header, transaction, block), each with its own threshold. Bans grow longer for repeat offenders, persist across restarts and expire on the verified clock. A ban for diverging across a checkpoint is capped, so an honest node on the wrong side of a fork can always return.

Objective invalidity, such as a bad signature, a draw secret outside its horizon or an invalid ticket record, is a strike. So is a header that builds directly on the receiving node's tip but is ineligible there, or carries an election seed that does not follow from the tip's: every node on that tip reaches the same verdict, and an honest node publishes a header only after checking it on its own tip. Five header strikes inside 18 hours ban the address. Every node checks a header before it relays one, so the peer that delivers a header is struck for it the same way whether it mined the header or relayed it. Drops an honest peer can cause are silent and never strikes: a header that no longer ranks on the receiving node, one refused for the receiving node's verification capacity or a full fork channel, and one whose verdict depends on a ledger view that differs between forks.

12. Synchronisation and checkpoints#

12.1 Initial block download#

A joining node downloads headers in batches and checks signatures and horizons in parallel, then fetches bodies in order and applies them strictly one at a time with the same block validation used at the tip, including each header's stake output or ticket record against the ledger built so far. Each candidate chain resolves its own beacons from its own headers.

Before switching to a candidate that forks below its tip, a node checks the candidate's headers whose stake had to exist before the fork point. For those heights every output or record that can count was created in the shared history, so the node checks each one against the ledger at the common ancestor, and every node reaches the same verdict. A candidate that fails is refused before anything is rolled back, and the peers that offered it are set aside.

That check covers the first two to three epochs above the fork point, while the download finds fork points up to 10,000 blocks deep. Past those heights a header may draw on stake created inside the candidate's own blocks, and judging it needs the bodies. So when comparing the two branches of such a fork, the node counts a block's work only if its stake output or ticket record existed at the fork point, on both branches and against the same ledger. Headers from keys that held nothing there count zero. A candidate that wins only on such headers is dropped before any body is downloaded, and no rollback is made on it. A deep rollback is weighed again on the exact ledger at the fork point before it is installed. A fabricated chain therefore cannot force a synced node to unwind its own chain.

Every block at every height is fully verified, signatures included; there is no "assume-valid" height. Download starts only with at least 8 sync peers, or 1 if a built-in bootstrap node is connected, and no flag or RPC can lower that, so an attacker who surrounds a node with its own peers (an eclipse) cannot relax it. The node keeps mining and relaying while it waits.

12.2 Mining is never paused by download#

If a candidate chain could pause mining, an attacker could advertise a fake heavy chain to halt honest block production and exploit the weakened window. A node on the tip of its main chain keeps mining unconditionally while a candidate chain downloads. A node whose main chain is itself behind the clock skips the slots it cannot sign at the right height (§4.5), which is a fact about its chain, not a pause for the download. If the download finds a better chain, the switch to it orphans the node's own blocks in the normal way.

12.3 Checkpoints#

Checkpoints sit on the 4,000-block grid (§6.2). Hard checkpoints pin settled history for nodes that have none of their own (a new node, a resync, a node offline for days): peers' claims of chain weight are unauthenticated and could otherwise lock such a node onto a fabricated heavier chain. This is the nothing-at-stake problem of unbonded proof of stake: signing costs nothing and nothing can be slashed, so a key that held stake at a fork point can sign a branch from that point at any later time, even after its owner sold the coins, and a private branch knows its own future beacons. Checkpoints are therefore permanent weak subjectivity, never retired.

Each release compiles in checkpoints the running network already holds as restoration pins, and between releases a pin file extends them. The node checks that file itself: it must name the network and genesis and carry signatures from a threshold of the checkpoint signers compiled into the binary, and it may add to the compiled-in table but never contradict it. Each signer confirms the hash on their own fully validated node, builds are reproducible, and every published pin can be checked independently.

13. Node and storage#

The reference implementation is a Rust workspace containing the node, a wallet, the miner key tool, the stewardship covenant and guardian tools, and an operator GUI.

A node keeps every block (archive), keeps recent bodies only (pruned, the default; pruned nodes can mine), or starts from a UTXO snapshot. An archive grows by roughly 2 TB a year at full 2 MiB blocks; a pruned node needs around 15–20 GB plus the headers, which grow by about 781 MB a year (§8.3). The UTXO set is held in memory; the relay fee floor rises with a transaction's size above 3,000 virtual bytes, which tracks the outputs it creates, so adding permanent entries is priced (§9.4). The published minimum node is 8 dedicated CPU cores, 8 GB of RAM, an SSD and a link whose round trip to its peers stays under about half a second.

The node serves one authenticated JSON-RPC interface with integer-only values. It is not Bitcoin-compatible: a Spek header has no difficulty, nonce, bits field or median time.

14. Governance and upgrades#

Spek has one upgrade mechanism: a header version that only increases, activated at a fixed flag height in a schedule compiled into the node and empty at launch. A signature-scheme or header-format change is always a hard fork and uses this path; tightening a rule uses it too, coordinated off chain. There is no version-bit signalling. Process governance is off chain and social; every full node enforces every rule; each operator independently adopts or declines an update.

Closest relatives. Two published designs are nearer to Spek than bonded proof of stake in general. Algorand (Gilad et al., 2017, reference 8) also picks stake-weighted participants secretly by a verifiable random function with no bond and no slashing, then settles each block by a committee vote, which gives fast finality but assumes an honest majority of the money and relies on elliptic-curve VRFs. Ouroboros Praos (David et al., 2018, reference 9) elects slot leaders secretly by VRF over the stake distribution, with an epoch nonce built from earlier chain data, and settles probabilistically like Spek. Spek differs in three ways: the secret is a committed hash chain rather than a VRF, so no elliptic-curve component sits in the election; a draw is one per stake output above a threshold rather than weight proportional to balance; and the beacon is fixed an epoch ahead from a seed that every winner extends, under the invariants of §4.7. Spek does not claim these differences make it safer than either design, and unlike both it has had no external review (§17).

Taken together, Spek offers:

  • no ASIC race;
  • no lock-up or slashing;
  • an ordinary computer is enough (the published minimum is 8 dedicated cores, 8 GB of RAM and an SSD);
  • one funded stake output keeps a key eligible for its whole 8.4-year horizon (renewal needs a second unit for the lead before the next horizon);
  • each funded stake address gets at most one draw per slot.

17. Known limitations and open items#

As of this version:

  • SQIsign is not a NIST standard. It is a Round 3 candidate in NIST's additional-signature process (§8.1). If later cryptanalysis weakens it, or NIST drops it, Spek's only remedy is a signature-scheme migration through a hard fork (§8.5, §14). Every operator chooses for themselves whether to adopt that fork.
  • No independent human review. The code, including the vendored SQIsign and RandomX C and the FFI boundary, has been reviewed only by AI models (Claude). No human security firm, cryptographer, or SQIsign author has reviewed it. Mainnet is its first exposure to outside attackers. That includes the uniqueness of the draw secret, on which the election depends: a related hash-based construction for proof-of-stake election, X-VRF, was later broken on exactly that property. §4.8 sketches why a second verifying draw secret would need a BLAKE3 collision; it is a sketch for a cryptographer to check, not a proof.
  • Nothing at stake. Signing costs nothing and unbonded stake cannot be slashed, so nothing stops a key that held stake at a fork point from signing a branch from that point later, including keys whose owners have since sold. Only restoration pins (running nodes) and compiled checkpoints (fresh nodes) bound it. On its own private branch an attacker also knows each beacon before that beacon's stake cutoff; simulation puts the break-even share at 0.44–0.46 for a branch inside the pin (the break-even share is the attacker share above which a private branch that picks its own beacon gains weight on the honest chain every epoch, so it can reverse any depth given time, and below which its odds fall with depth), and at about 0.38 (with a million candidate fits) for a fresh node that has no checkpoint past the fork.
  • Pins advance without network evidence. A restoration pin moves with the node's own tip, so a node partitioned, or mining alone, for longer than the pin lag (33–67 h) pins its own branch and refuses the other side on reconnect. For a network-wide partition that lasts that long, the split is permanent until operators choose a side: there is no automatic rejoin (§15).
  • No fast finality. A transaction is protected by its confirmations (Appendix B) until the pin; there is no finality gadget.
  • Download-time checks during the launch phase. Launch-phase eligibility needs the block bodies that hold the ticket records, so the header stage of a download checks signatures and horizons but no RandomX work. A fake launch-phase header chain is therefore as cheap to build as a fake post-launch one. The eligibility check before any rollback, the work comparison that counts only blocks backed at the branch point (§12.1), pins, block validation and the download's per-candidate budgets bound both. A fake chain still costs the node header storage and slot-root walks before it is dropped.
  • Stake keys are hot and public. Every header shows its stake key, and the key lives on the mining machine. The payout rule keeps one stake unit (one output worth the full requirement) per funded horizon at that address, so a key holds two stake units while the next horizon is funded ahead of a renewal, a year by default, and everything else goes to a hidden-key payout address. A node with no payout address configured keeps paying its stake address and warns daily.
  • Roughtime operator count. The built-in pool has four independent operators against a quorum of three: any one operator may be offline or rotating keys and syncs still complete, but with one offline every remaining operator must answer, and two colluding operators can steer the vote median (by at most the 5-second step bound per applied sync). The remedy is more independently operated servers, never a lower quorum.
  • Fee-only security is not analysed. Rewards halve every 4,200,000 blocks and stop when issuance reaches the cap (§10.1), after which miners are paid by fees alone. The stake requirement then sits at its 0.1-coin floor and an attack still costs the capital it must hold, but whether fee income alone keeps enough honest capital fielding draws has not been modelled.
  • Withholding the top five. A node ranks at most five peer headers per slot plus its own (§5). If the five best headers of a slot are all withheld, every node that holds them settles the same canonical null: no body in the top five is committable, and a node's own block ranked sixth is skipped because no peer retains it, so committing it would leave each miner on a different block. Safety holds: nodes can briefly disagree, because a node the withheld headers did not reach commits a real block while the others commit the null, but any real block outranks the null, so fork choice brings every node to the same block by a short reorganisation (§5) and no conflicting history survives. The slot's liveness is lost, and the withholder forfeits the slot's rewards. With an attacker share p of the draws for a slot, about p⁵ of slots are nulled; nulling a fraction f takes p = f^(1/5), that is p/(1−p) times the honest draw count: about 0.66× for 1% of slots, 1.7× for 10%, 6.7× for 50%. These are model estimates (independent uniform scores, every withheld header reaching every node), not simulation results. Each draw costs a recorded ticket per round in the launch phase and an aged stake output after it (§7).
  • Forced nulls and fork choice (resolved). Fork choice first summed raw scores. A null scores 0 while a slot's best real score sits close to the maximum, so one null outweighed many slots of ordinary score differences, and an attacker withholding the bodies of slots where it held the top five headers gained on the honest chain from about q = 0.13 at 100,000 draws. Fork choice now sums each block's work, the logarithm of its score's closeness to the maximum (§6.1), which moves that threshold to about 0.44–0.46, the range where a private branch already breaks even. The trade is deeper confirmations for the same protection (Appendix B), and a lower break-even share for a fresh node without checkpoints (about 0.38, down from 0.42), because a private branch's fitted keys now and then land very close to the maximum and work rewards that more than raw scores did.
  • Late release and selfish strategies are not analysed. A winner can release its header or body late, or to some peers only, and every miner knows its own scores for an epoch 12 hours ahead (§4.2). Appendix B models only a private branch; how much these strategies gain, alone or combined with a private branch, has not been measured.
  • Multiple draws per operator. One key per node is policy, not consensus. An operator holding K funded stake addresses (on one key or several) fields K draws for a one-time, refundable K × requirement. Whether the network's security then rests on capital held rather than on running costs turns on this, and it still needs a full economic analysis.
  • Not included: SPV proofs for light clients, native IPv6, data-availability sampling, on-chain soft-fork signalling, verification of a UTXO snapshot after sync, and NTS (authenticated NTP).
  • Hard checkpoints are a permanent trust assumption for nodes with no history of their own (weak subjectivity): such a node trusts the release's compiled-in pins and the checkpoint signer set. They have no sunset; the signer set, its threshold and the signing procedure are part of the launch disclosure.

Appendix B. Confirmations against an attacker share#

Probability that a transaction at k confirmations is ever reversible, for an attacker holding share q of the draws who may choose its fork point in hindsight. The model assumes the attacker's branch is scored against the same beacons as the honest chain, which holds for the first 1,441 blocks after its fork point. Beyond 1,441 blocks a private branch reads its own beacons, the case §17 treats with a break-even share of 0.44–0.46, so the tables stop at q = 0.40, whose depths (up to 679) stay inside 1,441. Forcing nulls on the honest chain does not help below about q = 0.44 (§6.1), so the model leaves it out. The figures come from a race model: the best of n independent uniform draws falls short of the maximum score by an exponentially distributed amount, a block's work is the logarithm of that shortfall (§6.1), so each slot moves the race between the two branches by ln(q/(1−q)) plus a logistic variable, and the attacker's branch wins a stretch of heights when its summed work exceeds the honest chain's. The probabilities are computed numerically (the law of the race's maximum on a fine lattice, saddlepoint tails for the sums), checked against Monte Carlo sampling, and the same method reproduces the closed forms of the earlier sum-of-scores rule exactly (reference 10).

Appendix C. Glossary#

Terms not in §1.2, in alphabetical order.

Term Meaning
Beacon height, stake cutoff The block an epoch's beacon is read from, and the height one epoch (1,440 blocks) below it. A stake output or ticket record counts for an epoch only if it was created below that epoch's cutoff (§7.1).
Bits The smallest unit: 10⁸ bits per coin.
Chainwork A chain's weight: the sum of the work of all its blocks, where a block's work is the logarithm of how close its score came to the maximum and a null block's is 0. Nodes follow the heaviest valid chain (§6.1).
Checkpoint A block hash on the 4,000-block grid that fixes history below it. A hard checkpoint is compiled into a release; a pin file adds newer ones between releases, signed by a threshold of checkpoint signers. A node without its own history trusts both (§12.3).
Coinbase The first transaction of a block, which pays the block reward and fees to the winner.
Draw secret root A random 32-byte secret in the miner's key file. Every draw secret is derived from it, and it is never published.
Election seed A value carried in every block header. Each block derives its seed from its parent's seed, its winner's key and its winner's draw secret. Beacons are read from it.
Equivocation A miner publishing two different headers for the same slot. The slot is cancelled for that miner (§4.6).
Fork window, reorganisation A reorganisation (reorg) replaces the newest blocks of a node's chain with a competing branch. The fork window is how deep a branch near the tip may fork and still be compared directly: 4 blocks (§6.2).
Hidden-key output An output that holds only a hash of its public key, so the key stays secret until the coin is spent (§8.4).
Mempool A node's pool of valid transactions waiting to go into a block.
Merkle root, Merkle path A Merkle tree hashes items in pairs, level by level, down to one 32-byte root that commits to all of them. A Merkle path is the sibling hashes from one item up to the root, enough to prove the item is under that root.
OP_RETURN output A zero-value output that carries data and can never be spent, so it never enters the UTXO set.
Open launch The public process that fills the genesis block with ticket records before the chain starts: the launch key every launch ticket is searched under, the sealed list of submissions, and the launch nonce that fixes the genesis. Its records alone make keys eligible in epochs 0–2 (§7.2).
Opening tranche The part of a genesis allocation spendable from coinbase maturity: 3% of each founder's share and the stewardship fund's 1,500,000 coins. Later tranches unlock year by year (§10.2).
RandomX, Roughtime RandomX is a memory-hard hash function built for ordinary CPUs, used only for launch-phase tickets (§7.2). Roughtime is an authenticated time protocol nodes take their clock from (§3.3).
Restoration pin A running node's own checkpoint: the grid block below which it never reorganises its chain. It trails the tip by 33–67 hours and needs no signature.
ρ The weight Level V witness bytes carry in virtual size, 3.02 (§9.4).
Round hash The block hash that keys one round of the launch-phase RandomX ticket search (§7.2).
SQIsign, BLAKE3 SQIsign is the post-quantum signature scheme every signature uses; Level I is the everyday size, Level V the larger custody size (§8.1). BLAKE3 is the hash function used everywhere (§8.2).
Stake program The 32-byte hidden-key program of a stake address, the form a launch-phase ticket names (§7.2).
UTXO Unspent transaction output: a coin. Every balance is a set of outputs not yet spent, as in Bitcoin (§9.1).
VRF Verifiable random function: a keyed hash that only the key holder can compute and anyone can check against the public key. Other proof-of-stake designs elect leaders with one; Spek uses a committed hash chain instead (§16).
Weak subjectivity A node with no history of its own has to trust a recent checkpoint from outside the chain, here a release's compiled checkpoints and signed pin files (§12.3).
Witness, virtual size A transaction's witness is its signatures and revealed keys and scripts. Virtual size is its size with Level V witness bytes weighted up, and is what fees and the block limit count (§9.4).
