Spek

A post-quantum, unbonded proof-of-stake ledger with a secret, ungrindable election every 30 seconds, and no energy race.

Technical white paper, November 2026. Describes the reference implementation (Rust, MIT / Apache-2.0). Designed by the founders, implemented, tested and reviewed entirely by Claude Code.

Two disclosures before anything else.

  1. SQIsign is not a NIST standard. It is a candidate in NIST's additional post-quantum signature process (advanced to Round 3 in May 2026, with evaluation expected to run about two years). "NIST security level 1" and "level 5" below name the security categories the parameter sets target, not approvals. NIST's finalised post-quantum signature standards (ML-DSA, SLH-DSA) and the selected FN-DSA are different schemes, and Spek uses none of them.
  2. The code has been built and audited only with AI models (Claude). The founders used Claude AI models to build and audit Spek. No independent human security audit, and no review by a cryptographer or by the SQIsign authors, has taken place before launch. That covers the Rust implementation, the vendored SQIsign and RandomX C code, and the FFI boundary between them. Anthropic, the maker of Claude, is not a partner in this project and does not endorse it.

Abstract#

Spek is a blockchain ledger in which time, not computing work, schedules blocks. The clock is divided into 30-second slots counted from a genesis timestamp, and every slot gets exactly one block. Each eligible stake output gets one secret draw per slot: a hash that only the key's owner can compute, over inputs that were all fixed before the randomness it is drawn against existed. The highest draw whose block is valid wins the slot. Nobody can predict the winner before its block header is published, and nobody can improve a draw by trying again, because there is nothing to try again. If no valid candidate arrives, every node builds the same null block, a block with no transactions, so the chain never stalls.

Taking part costs a held balance, not a power bill. After a 45-day launch phase, a key is eligible when its stake address holds one output worth at least 80% of the block reward, created at least a day earlier. Nothing is locked and nothing is slashed: the output is an ordinary coin, and spending it ends eligibility. During the launch phase, when nobody holds coins yet, eligibility is bought with RandomX computation instead: one recorded ticket per key per 3-day round.

Every signature is SQIsign, a compact post-quantum scheme, and every hash is BLAKE3. Public keys stay hidden behind hashes until coins are spent. Nodes take their time from an authenticated Roughtime quorum rather than the host clock. Transactions settle by confirmations sized to an assumed attacker share, and checkpoints bound how far history can be rewritten. Supply is capped at 450,000,000 coins: a 30,000,000-coin genesis allocation (founders 5%, vesting over five years; a stewardship fund 1.67%, vesting over twenty) plus a 50-coin block reward that halves every 4,200,000 blocks (about four years).

1. Introduction#

Every open blockchain has to decide who adds the next block, in a way an attacker cannot cheaply take over. Proof-of-work buys Sybil resistance (resistance to one party posing as many) with energy, and rewards whoever burns the most. Bonded proof-of-stake buys it with locked capital, and inherits a thicket of slashing, validator sets, and finality gadgets to police that capital. Spek is unbonded proof of stake: a per-slot election over stake outputs that each meet a coin threshold, with nothing locked and nothing slashed.

Three ideas carry the design:

  1. Time is the schedule. A block exists for every 30-second slot since genesis, whether or not anyone produced one. Height, timestamp, reward, fee floor, coin requirement and vesting are all functions of the slot number.
  2. One stake output, one secret draw. A miner's score for a slot depends only on values fixed before the draw's random beacon existed: its key, a secret it committed for that slot, and the height. There is no nonce to grind, no key to swap in after the fact, and nothing a block producer can re-sign or re-order to improve its own or any later chance. Until a miner publishes its header, nobody else can compute its score.
  3. Eligibility is the security parameter. Any selection rule over independent, uniform draws awards a party holding N of N+H draws exactly N/(N+H) of the slots. The only lever left is what a draw costs to field, and Spek prices that explicitly, in two phases (§7).

Stake in Spek is a threshold met by one ordinary output, never a bond: nothing is locked, burned or slashed, there is no validator set and no delegation, and there is no yield. The block winner earns the block reward. For the first 45 days eligibility is priced with RandomX tickets instead (§7.2); that work buys eligibility for a round, never a block, so the chain is not proof of work even then. The result is a network whose honest operating cost is a node and a held balance.

1.1 One slot, start to finish#

  1. A new slot opens every 30 seconds. Its number is the height of the block it will produce.
  2. Each miner with an eligible key (§7) computes its score for the slot: one hash of the epoch's beacon, the height, its public key and its slot secret for that height (§4).
  3. For the first 6 seconds only block headers travel. Each node ranks the headers it receives by score.
  4. From 6 to 30 seconds nodes fetch the full blocks of the best few candidates and validate the best one.
  5. When the slot closes, each node commits the highest-ranked candidate whose full block is valid. If there is none, every node builds the same null block (§5).
  6. The winner's slot secret is mixed into the chain's election seed, from which a later epoch's beacon is read (§4.2).

1.2 Terms#

2. Design goals#

  • Post-quantum by construction. SQIsign for every signature (Level I for headers and everyday outputs, Level V opt-in for long-lived custody), keys hidden behind hashes until spent, no elliptic-curve code in the signing code, and a versioned migration path (§8.5).
  • No computational waste. One BLAKE3 evaluation per stake output per slot decides candidacy; producing the slot secret costs fewer than 96 hashes. Signing costs 25–40 ms once per slot; verifying a header costs one SQIsign verification (2.7–5.0 ms) plus a walk of at most 8,651 hashes (0.9–2.6 ms).
  • Ungrindable, unpredictable election. Every score input is fixed before the beacon it is drawn against exists, and each winner adds secret entropy to a later beacon. No winner schedule exists to read ahead of time, so there is no predicted winner to target.
  • Deterministic everything. Timestamps, rewards, tie-breaks, null blocks and genesis bytes are identical on every node. SQIsign signatures are randomised, so the protocol keeps them out of everything that must be deterministic.
  • Plain settlement claims. Forks near the tip are compared within a 4-block window (about 2 minutes). Transactions settle by confirmations sized to an assumed attacker share (Appendix B), and a running node never reorganises below its restoration pin (33–67 h). There is no finality gadget.
  • Fail fast. Cheap structural checks reject bad input in microseconds; expensive checks run only on the top-ranked candidates.
  • Plain governance. One upgrade mechanism (block version and flag height), no on-chain voting, a published multisig council for the stewardship fund.

3. Timeslots and the verified clock#

3.1 Slots#

With genesis timestamp G, the slot being mined now, which is also the height of the block that does not exist yet, is

current slot       = ⌊(now − G) / 30⌋        unsettled: being mined
settled tip        = current slot − 1        the newest block that can exist
timestamp(h)       = G + 30·h

The header has no timestamp field: a block at height h can only have timestamp G + 30h. That removes timestamp manipulation, median-time-past rules and tolerance windows by construction. Block height is a u32 (about 4,000 years of 30-second slots); derived timestamps are 64-bit.

Slots are grouped into epochs of L = 1,440 slots (12 h), which carry the election beacon (§4.2), and segments of S = 8,640 slots (3 days), which carry each key's slot-secret hash chains (§4.1).

3.2 Two phases per slot#

Each slot has a headers-only phase (0–6 s), in which 743-byte candidate headers flood the network and the ranking settles, and a block phase (6–30 s), in which nodes fetch full blocks only for the top three candidates (rank 1 from three peers, ranks 2–3 from one each) and serve the top five. Because bodies move only after the ranking is known, unranked blocks cannot waste bandwidth. The 24-second body window fits megabyte-scale blocks crossing intercontinental links, with room for two retry rounds.

0 s                6 s                                                   30 s
|--- headers only --|--- pull top-3 bodies · validate rank-1 · serve top-5 ---|
slot h opens                                        boundary: winner of h committed, or null

3.3 Where time comes from#

A wrong clock puts a node in the wrong slot, so Spek does not take consensus time from the operating system. Each node keeps its own verified clock:

  • Source. Roughtime, an authenticated time protocol. Every response is authenticated end to end: the server's long-term Ed25519 key signs a delegation certificate, the delegated key signs the response, the node's own request is bound into the signed reply (so a recorded reply cannot be replayed), and the reported time must sit inside the delegation's validity span.
  • Quorum. Servers are queried in parallel and every sample is corrected for round-trip time. Each operator (whoever holds the keys) casts one vote, the median of its own samples, however many addresses it runs. Votes more than 2 s from the median of votes are discarded, at least 3 voting operators must remain (a node may be set to require more, never fewer), and the median of the surviving votes is adopted, rounded to whole seconds.
  • Between syncs. Verified time is carried forward on the raw hardware oscillator, not on the system clock the host's NTP daemon adjusts. Raw oscillators run 30–100 ppm off on ordinary and cloud hosts, so the node learns its oscillator's rate from successive syncs and corrects for it. Each sync may move the learned rate by at most 50 ppm, and the rate is clamped at 250 ppm, so a steered quorum cannot install a large false rate in one step.
  • Cadence. A node syncs hourly while it learns its rate, and every 4 h once a sync confirms the rate to within 5 ppm (at most about 72 ms of drift over the interval). A sync that shows the rate has changed (a migrated virtual machine, for example) drops it back to hourly.
  • Step bound. A new median is accepted outright only within 5 s of where the node's clock already is. Larger backward steps are refused; larger forward steps need corroboration, either from the node's own measured drift (the suspend-and-resume case) or from a second sync at a higher quorum.
  • Mining hold. A node that has never acquired a verified time does not sign blocks. Relaying, serving and syncing continue. An opt-out exists for the case where every configured server is down, and it is loud.

Consequence. Agreement between nodes' clocks is bounded by the residual after rate correction over one sync interval plus Roughtime path asymmetry, not by a "sub-second" promise. The 2-second outlier bound, the 5-second step bound and the 30-second slot are sized around that.

4. Leader election#

The election needs a per-slot value that is (a) secret until used, (b) unique per height, so it cannot be ground, and (c) committed before the randomness it is drawn against exists. Spek builds it from BLAKE3 alone, with committed hash chains.

4.1 Slot secrets and horizons#

Each miner key file holds a SQIsign Level I key pair and a 32-byte slot seed drawn from the operating system's random source when the key is generated (385 bytes in all). The slot seed is independent of the signing key, so recovering a SQIsign secret key reveals nothing about future slot secrets.

σ       = BLAKE3-derive-key("spek 2026-10-20 slot-secret v1", slot_seed)
s_g     = BLAKE3("spek/slot-chain/v1" ‖ σ ‖ g)                 // one chain per 3-day segment g
T_g     = step^S(s_g)                                          // segment top, step = BLAKE3("spek/slot-step/v1" ‖ x)
r_h     = step^(S − 1 − (h mod S))(s_g(h))                     // slot reveal for height h
leaf_j  = BLAKE3("spek/slot-leaf/v1" ‖ pk ‖ T_(J0 + j))         // j = 0 … 1023, key-bound
C       = Merkle root over the 1,024 leaves                    // one horizon

Each segment's chain is revealed backwards, one value per slot, so publishing r_h exposes only values for heights already passed. A horizon is 1,024 consecutive segments starting at segment J0: about 8.4 years. Its root C, bound to the key in every leaf, is committed in the stake output (§7.1) before any beacon it will be drawn against exists, so for every key, commitment and height exactly one r_h verifies.

A header carries the reveal, its 10-hash Merkle path and J0. A verifier walks the reveal up to its segment top (at most S hashes), hashes the key-bound leaf, climbs the path, and uses the root it derives to rebuild the stake address. If the reveal is wrong, there is simply no stake at that address. The root itself is never carried. A mining node keeps the 1,024 segment tops (32 KB) and checkpoints within the current segment, so producing r_h takes fewer than 96 hashes; building a horizon takes 1–3 s.

A node creates its next horizon automatically about a year before the current one ends (122 segments by default, an operator setting), with two segments of overlap so eligibility never lapses.

4.2 The epoch beacon#

B_e = BLAKE3("spek/beacon/v1" ‖ e ‖ genesis.merkle_root)                 e ∈ {0, 1}
B_e = BLAKE3("spek/beacon/v1" ‖ e ‖ election_seed@beacon_height(e))      e ≥ 2
beacon_height(e) = (e − 1)·L − 1

The beacon for epoch e is read from the election seed at the last block of epoch e−2, a full epoch before e starts. Every block of that source epoch mixes its winner's secret r_h into the election seed (§4.4), so the beacon is unpredictable until the source epoch has been produced. It is the same on every fork that shares that history, which covers every fork near the tip (at most 5 deep, against L = 1,440). The two launch epochs read the genesis merkle root, which commits to the launch ticket records and a launch nonce derived from a Bitcoin block mined after the record list was sealed (§7.2), so nobody, the organiser included, could choose it knowing the launch beacons.

The miner at a beacon height can withhold its block and let the runner-up set the beacon instead, and because it holds its own future reveals it can evaluate both choices. Simulation puts the gain at 1.9–3.0% more of its own wins per beacon it controls, 0.3–0.6% averaged over all epochs, with no compounding.

4.3 The score#

score = middle_out( BLAKE3("spek/score/v2" ‖ B_e ‖ h ‖ pk ‖ r_h) )
x = hash as a 256-bit integer,  C = 2^255
middle_out(x) = x ≥ C ? (x − C) + 1 : C − x          // range [1, 2^255], arbitrary-precision integers

Both 0x00…00 and 0xFF…FF score the maximum; 0x7F…FF and 0x80…00 score 1. The genesis block scores the fixed 2^255; a null block scores 0.

0x00…00                         C = 2^255                          0xFF…FF
|==================================|==================================|
score 2^255 (max)              score 1 (min)               score 2^255 (max)
            higher score = further from centre = more likely to win

Every input is fixed before the beacon exists: the key and its commitment sit in a stake output that had to be created below a cutoff one full epoch before the beacon height (§7.1), and r_h is the unique reveal of that commitment. The key is inside the hash, so a copied commitment or a replayed reveal gives the copier an independent draw, never the victim's score. A genuine tie between two distinct keys has probability about 2^−255; the tie-break (highest score, then lowest public key, then lowest merkle root) makes the outcome deterministic and offers nothing to grind.

A node checks a received header cheapest first:

  1. Shape. Exact length and a valid version.
  2. Claimed score. One hash over the header's key and reveal. A header that could not enter the slot's top five is dropped here, before any expensive check, and is not relayed.
  3. Signature and reveal. On the validation pool: the SQIsign signature, then the reveal walk up to the horizon root. A reveal outside its horizon fails before any hash is computed.
  4. Candidacy. The election seed must follow from the parent's, and the stake address rebuilt from the derived root must hold an eligible output (§7).

A header enters the ranking only after steps 3 and 4 pass, so an unverified claim can never displace a verified entry. A junk header with a made-up reveal costs at most one signature check, one walk and one bounded stake lookup, whether or not its sender holds stake. With top-5 relay a node verifies about 5·(1 + ln(N/5)) headers per slot for N miners: about 31 at a thousand miners, 66 at a million.

4.4 The election seed chain#

The header carries two hash chains with different jobs. prev_block is the identity chain: the BLAKE3 hash of the parent's signed fields. It leaves the signature out, because anyone holding a SQIsign signature can derive another valid one over the same bytes. election_seed is the beacon chain:

election_seed(h) = BLAKE3("spek/election-seed/v2" ‖ election_seed(h−1) ‖ miner_pubkey ‖ r_h)
election_seed(0) = 0x00…00

The seed binds only the parent's seed, the winner's key and its committed reveal. No signature, merkle root or header hash enters it, so re-signing or re-ordering a block cannot move any later beacon.

4.5 Mining a block#

At each slot boundary a mining node, reading the parent, its seed, the beacon and the stake ledger from one consistent chain state:

  1. checks that it is in sync: its tip must be the previous slot (chain_height + 1 == current_slot), so a node behind the clock does not sign a block at the wrong height. This is not a pause during block download, which the protocol forbids (§12.2);
  2. picks its eligible horizon (in the seed phase, the one whose stake program holds the round's ticket record);
  3. computes r_h and its Merkle path, then the score and the next election seed;
  4. checks its own eligibility with the same rule block validation uses, and skips the slot rather than produce a block every peer would reject;
  5. builds a block from the mempool and checks it (structure, locktime, genesis spend rules, size and count limits, merkle root);
  6. signs the first 543 bytes of the header with SQIsign;
  7. saves the signed attempt to disk, so a restart within the slot re-announces the same header instead of a second, different one (§4.6);
  8. broadcasts the header.

4.6 Equivocation#

Each node keeps only one entry per miner key per parent per slot. Because the block hash leaves the signature out, a second header with identical signed content is the same block, and the two are merged. A second header with different signed content for the same attempt is equivocation: the miner's entry is removed, the attempt is cancelled for the slot under its attempt-identity hash BLAKE3(prev_block ‖ miner_pubkey) on every node, and a compact proof is gossiped so every node reaches the same verdict.

4.7 What the election guarantees#

Together, §4.1–§4.6 and the eligibility rules of §7 give the election these properties:

  • The same draw on every nearby fork. Two chains that share every block up to an epoch's beacon height give each key the same score at each height of that epoch. Every fork the network resolves near the tip shares that history.
  • A seed nobody can steer. The election seed, and every beacon read from it, depends only on the previous election seed, the winner's key and the winner's committed reveal. A producer can change nothing else in its block that moves them.
  • Inputs fixed before the beacon. A stake output or ticket record counts only if it was created a full epoch before the beacon height, so a key and its commitment are fixed before the randomness they are drawn against exists.
  • One value per height. For each key, commitment and height exactly one reveal verifies, so there is nothing to try again.
  • One draw per stake address and horizon. A stake address is built from the key and one horizon's commitment, so it belongs to exactly one horizon, and each eligible header names one horizon and one output at its address holding a full stake unit. Draws therefore scale with funded stake addresses, not with keys. One key with two funded horizons holds two draws per slot, the same as two keys: its miner computes both scores and publishes only the better header, so the network sees one header and no equivocation (§4.6). Two draws cost two full requirements, because one output counts for one address only and moving coins between addresses restarts their aging.
  • Draws bound to the key. The key is inside both the score and every commitment leaf. A copied commitment is invalid under any other key, and a replayed reveal gives the copier its own independent draw, never the victim's score.
  • Slot secrets independent of the signing key. The slot seed is separate random bytes, so recovering a SQIsign secret key reveals no future reveal.
  • No guessed beacons. Every score is computed under a beacon read from the chain being scored (§6.1); a header whose beacon cannot be read yet is held aside, never scored with a guess.

5. Slot settlement and the null block#

At the slot boundary, each node goes through its retained candidates in rank order (up to the top five) and commits the first whose full body is in hand and passes full validation. Holding five candidates while fetching three leaves backups for a top candidate that is invalid or whose body never arrives. A node waits at most 2.5 s for the rank-1 verdict if it is still being computed.

If a slot closes with no committable candidate, every node builds the canonical null block for (height, prev_block): version 1, all-zero miner key, signature and slot fields, zero merkle root, no transactions and no coinbase. Its election seed is derived by the normal rule with a fixed null identity and an all-zero reveal, so the beacon chain continues unbroken. It is built, not mined, so nothing crosses the network. Its score is 0, below the minimum real score of 1, so any real block for that height outranks it: if a late winner surfaces, fork choice replaces the null with a reorganisation of depth 1, with no ban and no penalty. Null blocks mint nothing and are stored and served like ordinary blocks.

Residual. Settlement at each slot boundary settles one slot. If every node misses two or more boundaries at once (a coordinated restart, a network-wide freeze), no node is exactly one slot behind and the chain stops. Recovery is an operator-run RPC call that fills deterministic null blocks for settled slots, capped per call at the 4-block fork window and refused whenever any peer proves a better chain exists. It cannot be automatic: a single node cannot tell "the whole network was down" from "I was down".

6. Chain selection and settlement#

6.1 Cumulative score#

chainwork(b) = chainwork(parent(b)) + score(b)       // score under the beacon of b's epoch on that chain

Chainwork is an arbitrary-precision sum that is never truncated or reset. Each block is scored against the beacon of its epoch on the chain being scored, resolved from that chain's own headers; a header whose beacon cannot yet be resolved is held aside, never scored with a guess.

  • Live headers are scored under the main chain's beacons. A header for an epoch other than the current or the next one is held aside, never ranked.
  • Forks near the tip are at most 5 blocks deep, far less than an epoch, so the block their beacon comes from is always shared with the main chain.
  • Candidate chains in download read each epoch's beacon from their own headers once they fork below that epoch's beacon height. Until that header has arrived, the candidate's weight is unknown, and a node never switches to a chain of unknown weight.

6.2 Fork resolution#

  1. Forks near the tip. When a competing branch forks within the fork window (PROPAGATION_FORK_WINDOW = 4 blocks below the tip), the two branches are compared by cumulative score once each holds at least two blocks above the fork point; the heavier wins and the other is dropped. Waiting for both sides avoids switching back and forth on every block. The reorganisation is checked against a copy of the ledger before any live state changes, so an invalid fork block leaves the chain untouched. Rollback on this path is bounded at 5 blocks.
  2. Deeper forks. If no common ancestor lies inside the window while the peer's chain keeps pace with the clock (which is what both sides of a healed network partition look like, since both mine every slot), the node switches to a full download, finds the true branch point, compares cumulative score, and reorganises at any depth above its restoration pin.
  3. Checkpoint barrier. A fork whose branch point lies behind the node's restoration pin or a hard checkpoint is never resolved automatically, and the peer offering it is banned. Checkpoints sit on a 4,000-block grid (about 33 h), and the restoration pin is the newest grid boundary buried at least one full interval below the tip, so it trails the tip by 33–67 h. Only a partition that outlasts a boundary by more than an interval leaves the two sides with different pins; that state needs operator recovery.

Coinbase outputs mature after 3,000 blocks (about 25 h).

6.3 Settlement#

Spek has three settlement layers:

  • Confirmations (probabilistic). Draws are fixed per height, so an attacker can rewrite history only by out-scoring the honest chain over the same heights. Appendix B gives the confirmations needed for under one reversible slot per century against an attacker holding share q of the draws who may choose its fork point in hindsight: 37 confirmations (18 min) at 20%, 136 (68 min) at 33%, 412 (3.4 h) at 40%. Integrators choose their depth from the share they want to tolerate.
  • Restoration pins (per node). A running node never reorganises below its pin, which trails the tip by 33–67 h.
  • Checkpoints (weak subjectivity). A node with no history of its own trusts the checkpoints compiled into its release and pin files signed by a threshold of checkpoint signers (§12.3).

There is no finality gadget and no rollback limit shorter than the pin.

7. Eligibility: ticket records and stake outputs#

No election rule over independent draws can stop one party from fielding many draws, so the cost of fielding a draw is where Spek's security lives. That cost has two phases, and in both the thing that makes a key eligible must be on chain before the beacon it competes against.

7.1 After the seed phase: one stake output#

min_coin_requirement(h) = max(0.8 × block_reward(h), 0.1 coin)     for h ≥ 129,600
stake_address           = hidden-key address of (pk, BLAKE3("spek/slot-commit/v1" ‖ C ‖ J0))
stake_cutoff(h)         = beacon_height(epoch(h)) − L

A header at height h is eligible only if its horizon covers h and its stake address, rebuilt from the header's key and the root its reveal derives, holds one unspent output that:

  • is worth at least the requirement (several smaller outputs do not add up);
  • was created below stake_cutoff(h), one full epoch below the beacon height, so new stake first counts about 24–36 h after it is created;
  • if it is a coinbase output, is mature.

Eligibility is judged against the parent block's ledger, so spending the stake output ends eligibility from the next block, and on a fork each branch's own ledger decides. Counting one output per draw keeps the check to a short walk of a value-ordered index: every output it steps over holds at least a full requirement, so filling a stake address with dust cannot slow anyone's check. A stake address belongs to exactly one horizon, so each funded horizon is its own address with its own output and its own draw per slot. A key with two funded horizons holds two draws, which costs two requirements, economically the same as two keys: one output counts for one address only, and moving coins between addresses restarts their aging.

After the seed phase, block production is capital-proportional: a holder of X coins can fund ⌊X/requirement⌋ stake outputs and wins slots in that proportion. The requirement sets the size of one draw, not the cost of an attack: matching the honest network costs roughly the capital it holds, whatever one draw costs. The requirement halves with the reward, and the 0.1-coin floor only binds about nine halvings (about 36 years) out.

The stake key is public in every header its miner publishes and lives on the mining machine, so the node keeps exposure to one stake unit. By node policy (not consensus), the coinbase pays the stake address of the first horizon not yet funded, then a separate hidden-key payout address. A winner therefore funds its next horizon for free; a key that never wins renews with one ordinary transaction, which the node makes itself from any surplus at the current stake address about a year before the horizon ends, or which the operator funds from a wallet. The node also merges a stake address funded in pieces into a single output.

Renewal is a transaction. A miner that never wins keeps its eligibility by funding the next horizon's address with an ordinary transaction, at least one requirement, created early enough to age. The node builds the next horizon about a year ahead, and funds it itself from any surplus beyond the counted output at the current address; a node holding exactly one requirement needs a transfer from a wallet. Nothing is locked, so once the new output is aged the old one can be spent. A miner that wins a block gets the next horizon funded by its coinbase.

This also avoids the classic proof-of-work death spiral. Honest operating cost is close to zero, so a falling price gives no miner a reason to switch off, and the honest draw count does not collapse with the price. Price exposure sits on the attacker's side: buying a large share drives the price up as it buys, and the stake it holds loses value when the attack is seen.

7.2 Seed phase: RandomX ticket records#

At launch nobody holds coins, so a coin requirement would be zero and a draw would cost one SQIsign key generation (sub-second, parallel, pre-computable). The first 45 days (129,600 blocks) therefore use a different price. The seed phase is divided into 15 rounds of W = 8,640 blocks (3 days). A ticket is a nonce such that

RandomX_K( "SPEK-SEED-TICKET-V2" ‖ round ‖ round_seed ‖ A ‖ nonce ) < D,   D = 2^228
A            = the stake program (the 32-byte hidden-key program of the miner's stake address)
K            = genesis hash (fixed for the whole seed phase)
round_seed_0 = genesis hash
round_seed_1 = hash of the block at height W/2
round_seed_r = hash of the block at height (r−1)·W          for r ≥ 2

A ticket counts only once it is recorded on chain: a 48-byte record ("SKTR" ‖ round ‖ A ‖ nonce) carried as a zero-value OP_RETURN output in a seed-phase coinbase, at most 16 per block, one per (A, round) on the chain, each for the current or the next round. A block with an invalid record is invalid, and after the seed phase a coinbase may carry none. Records travel on their own gossip topic and wait in a bounded pool; every block producer includes pending ones. A record counts for an epoch only if it landed below that epoch's stake cutoff, so to cover a whole round it must land about two epochs before the round starts (a 48-hour search window per round). Because the ticket is committed before the beacon it competes against exists, a miner cannot rank free keys by their scores in an already-known epoch and buy tickets only for the best ones.

The RandomX instance is a Spek variant with its own parameters, so rented hash power built for other chains cannot be pointed at it. Verification runs in light mode (15–30 ms, 256 MiB cache); searching uses the dataset of about 2 GiB. D was set so that a 2018-era 8-core desktop's spare cycles yield about three tickets per round; a slot in which no ticket holder is eligible gets the null block.

A round's seed is read from the candidate chain's own ancestry, so a ticket's validity depends only on the block and its chain, and re-checks identically during download. Round 1 is seeded from the middle of round 0 rather than from genesis, so a pre-launch search can buy at most one round of tickets, not two.

Open launch. Epochs 0–2 (the first 36 hours) count only records written into the genesis coinbase, and anyone can win one:

  1. Open. The search opens at a pre-announced Bitcoin block. Its hash, with the network name, gives the launch key K_L, so no ticket can exist before it.
  2. Search and submit. Anyone searches for a round-0 ticket under K_L (the same target D, with K_L as the RandomX key and round seed) and submits the record to a public submission channel. The channel checks each ticket on arrival and lists every valid entry with its ticket hash, so anyone can recheck the listing.
  3. Seal. After the deadline the organiser publishes the sealed list with the genesis timestamp (6 hours after the deadline), the genesis message and the allocation, a digest over all of them, and the height of a Bitcoin block six blocks past the tip at that moment. Independent witnesses (anyone may witness) record the digest before that block is mined.
  4. Select. The genesis takes up to 1,973 records, one per key, lowest ticket hash first, so when more are submitted than fit, searching longer buys better odds.
  5. Derive. The launch nonce is derived from the launch key, the seal digest and that Bitcoin block's hash, and the genesis builder is deterministic. The launch beacons therefore depend on a value nobody knew while any input could still change, and anyone can recompute the selection and the genesis block from public inputs.

One record is one key, and a node mines one key, so a launch seat costs what every later round costs: one ticket.

Seed-phase draws are therefore priced by sustained work per round rather than one-time key generation: a bank of keys is worthless without fresh work per key per round, and a flood of keys fades within two rounds once its operator stops paying for it. Ticket holders must fund a stake output below the cutoff of the first epoch after the seed phase; the node warns seven days ahead.

7.3 What the schedule does and does not do#

Both phases award blocks in proportion to the draws held. After the seed phase, draws are bought with coins that (apart from trading) only block rewards create, so the distribution of coin shares at the end of the seed phase carries forward under the election. Shares change afterwards only when coins change hands. One key per node is client policy, not consensus: nothing ties a miner key to a machine, and the economics do not depend on it.

8. Cryptography#

8.1 Signatures: SQIsign Level I and Level V#

Every signature in the system is SQIsign (isogeny-based), produced by a vendored reference implementation behind an FFI boundary. There is no ECDSA, no Schnorr, and no elliptic-curve library linked into the signature code, and a test on the dependency graph keeps it that way.

Level Target Public key Signature Secret key Verify (ADX / portable) Used for
I NIST level 1 83 B 200 B 270 B 2.68 / 5.03 ms Headers, mining keys, stake outputs, everyday outputs (the default)
V NIST level 5 169 B 406 B 549 B 16.4 / 26.7 ms Opt-in custody outputs; every genesis allocation, council and guardian key

Signing a Level I header takes 25–40 ms, once per slot for a miner; the signer verifies its own signature before releasing it. ADX is the faster arithmetic backend on recent x86 processors; portable is the plain C fallback.

Level I headers. A forger who broke Level I still could not win a live slot as someone else, because it would also need that key's unrevealed r_h, which comes from an independent slot seed and is protected only by BLAKE3. It could copy a just-revealed r_h into a second header and force the slot to be cancelled as equivocation (a liveness attack, not a theft), and it could sign branches for past heights down to the restoration pin, which would hold at any level that broke. The payout rule keeps one stake unit per key (§7.1). Mining keys rotate with every horizon, so moving headers to a new level later is a hard fork that phases in as horizons expire, with no coin moves.

Standardisation and review status. SQIsign is not a NIST standard. NIST advanced nine candidates to Round 3 of its additional digital-signature process in May 2026; one of them, HAWK, has since been withdrawn by its submission team, leaving eight, and SQIsign is among them. That round is expected to last about two years, a draft standard could not appear before about 2028, and SQIsign may be dropped. "Level I" and "Level V" refer to the security categories the parameters target (comparable to AES-128 and AES-256 key search), not to any NIST approval. Spek uses SQIsign rather than the standardised ML-DSA for its size: a 200-byte signature and an 83-byte key against roughly 2.4 KB and 1.3 KB. The trade-off is that SQIsign's security rests on a younger assumption (the supersingular endomorphism-ring problem) with less cryptanalytic history than lattices, and on a reference implementation that was not built for production. Spek's copy of that implementation and its Rust FFI boundary have been audited only by AI models (Claude). No cryptographer, SQIsign author, or independent human auditor has reviewed them before launch.

A public key has exactly one valid encoding: every field element must be canonical (below the field prime), and the starting curve E₀, whose endomorphism ring is public, is never an acceptable key. A non-canonical encoding is a decode error, never silently corrected. A verification cache (262,144 entries) remembers only valid signatures, so re-presented valid signatures cost a hash lookup; it never caches failures and never changes a verdict.

8.2 Hashing: BLAKE3#

BLAKE3 is used for block hashes, election seeds, beacons, scores, slot secrets and their Merkle trees, transaction merkle trees, script and hidden-key commitments, the OP_BLAKE3 opcode, addresses, and the UTXO script index. Every consensus hash is domain-separated by a tag string. Transaction merkle trees tag leaves (0x00) and interior nodes (0x01) so no byte string can be valid as both; odd levels duplicate the last node, and a block may not contain the same transaction id twice.

8.3 Block header#

The signature covers every other field, not just the score inputs, so nobody can attach a different transaction set to a winning header. The encoding is a fixed 743-byte layout; trailing bytes are rejected. Headers grow by about 781 MB a year, however many miners there are. The horizon root is derived, never carried; seed-phase tickets live in coinbase records, not the header; there is no reserved header field.

8.4 Hidden keys and script commitments instead of Taproot#

Taproot hides a script tree by tweaking an elliptic-curve key. Isogeny keys cannot be tweaked that way, so Spek's analogue, ScriptCommit, commits to the script tree with a hash:

commitment = BLAKE3(T ‖ T ‖ pubkey ‖ script_merkle_root),  T = BLAKE3("SpekScriptCommit")
key-path-only outputs use commitment = 0x00…00

The default output hides even the key. A hashed output is 34 bytes, a witness version and a 32-byte program, the same shape as a Bitcoin P2WSH or P2TR output:

v1 (Level I):  OP_1 <32 B>   program = TH("SpekHashedCommit",   pubkey83  ‖ commitment)
v2 (Level V):  OP_2 <32 B>   program = TH("SpekHashedCommitL5", pubkey169 ‖ commitment)

A key-path spend reveals the key and commitment next to one signature. A script-path spend reveals the leaf, its merkle proof and a control block; the node recomputes the commitment and the program before running the leaf in the script machine (§9.3). Leaves under a v2 output verify Level V signatures. Multisig, timelocks, hash locks and atomic swaps can be expressed; key aggregation cannot. The plain ScriptCommit output (OP_1 <83-byte pubkey> <32-byte commitment>, 118 bytes) remains valid for outputs that want the key visible.

Addresses are Bech32m with the prefix spek: witness version 1 carries a 32-byte hashed program or the 115-byte plain program, and version 2 a 32-byte Level V program. Decoding re-encodes and requires a byte-exact match, so each output script has exactly one lowercase address string. Wallets use the hashed form for every receive, change and coinbase address, so a public key is exposed only when its output is spent. The exception is a stake key, which every header it signs makes public.

8.5 Crypto-agility#

There is no per-transaction choice of algorithm and no runtime negotiation: at any height exactly one scheme is valid for a given output form or header version, which rules out downgrade and algorithm-confusion attacks. The witness version selects the output scheme (1 = Level I, 2 = Level V; versions 3–16 are reserved), and the block version selects the header scheme, activated through the height-indexed upgrade schedule (§14). Because the signed message commits to every spent output's locking script, a signature for one scheme can never be reinterpreted under another. A hash-committed output is the shape other chains are adding for a post-quantum migration; Spek starts with it, and with a second, larger parameter set already live for custody.

9. Transactions and scripts#

9.1 Model#

Spek is a UTXO ledger: coins are unspent outputs of earlier transactions, as in Bitcoin. Values are unsigned 64-bit integers counted in bits (10⁸ bits per coin); there is no floating point anywhere in the protocol or its RPC. Exactly four output forms can be created: hashed Level I (34 bytes), hashed Level V (34 bytes), plain ScriptCommit (118 bytes), and zero-value OP_RETURN data outputs, which never enter the UTXO set. There is no pay-to-pubkey form. Everything else is rejected, in blocks and in the mempool, because an unspendable output would burn its coins forever.

The transaction id is the BLAKE3 hash of every field except the witnesses (the signatures and revealed data), so it is fixed before signing and no relay can change it; the block merkle tree commits to a second hash over the full encoding, witnesses included. The signed message commits to the chain (its genesis block hash), the inputs, the outputs, every spent output's value and locking script, and the version, but not to the witness. Committing to the chain matters for offline signers: the same keys produce byte-identical scripts on every chain, so without it a signature made on a test chain could be valid on mainnet. A spend's transaction id is stable only while its witness is the only one that satisfies it, so validation enforces a full canonical form: canonical witness encoding, minimal numbers, a clean stack, minimal conditionals, and one signature rule under which a non-empty signature that fails verification aborts the script rather than evaluating to false. Every signature signs the whole transaction (SIGHASH_ALL); there are no other signature modes.

9.2 Time locks#

All locks are block-height locks; there is no timestamp variant, because height is time. Absolute nLockTime, relative nSequence locks (as in Bitcoin's BIP68, version 2 and up), OP_CHECKLOCKTIMEVERIFY and OP_CHECKSEQUENCEVERIFY are enforced with one spending-height rule shared by block validation and the mempool: the height the transaction would be mined at.

9.3 Script machine#

A minimal stack machine runs ScriptCommit leaves: 82 opcodes, frozen per leaf version (0xc0). OP_BLAKE3 sits on Bitcoin's SHA-256 byte, and OP_SHA256 at 0xbb, so cross-chain atomic swaps can share one hash lock with Bitcoin-family chains. OP_CHECKSIG, CHECKSIGVERIFY and CHECKSIGADD verify SQIsign at the level of the output's witness version; Bitcoin's CHECKMULTISIG opcodes are disabled. Limits: 10,000-byte scripts, 1,000-item stacks, 520-byte elements, 100-deep conditionals, 128-deep merkle proofs. Signature verification is the dominant cost and a failed signature cannot be cached, so each input carries a signature budget (213 witness bytes per Level I verification, 421 per Level V verification, charged before the verification): an attacker-written leaf cannot make a node do more than about one verification per genuine signature's worth of witness bytes. Everything else a script can do costs under 2 ms per input at the limits.

9.4 Virtual size, fees and the mempool#

A Level V verification costs up to 6.119 times a Level I verification, so each Level V input's witness bytes count ρ = 151/50 = 3.02 times in a transaction's virtual size. Blocks are limited to header + Σ vsize ≤ 2 MiB, and every fee rate is measured in virtual size, so no block can take longer to verify than a full Level I block. For a transaction with no Level V input, virtual size equals its size in bytes.

A relay fee floor (250,000 bits at launch, falling each halving era) is flat for transactions up to 3,000 virtual bytes and rises linearly above that, so occupying the UTXO set permanently is priced while ordinary payments are not. The mempool is bounded (200 MB and 100,000 transactions by default). Block templates fill 85% of a block by fee rate and the rest oldest-first, and a miner's coinbase claims the block reward plus fees, never more. One transaction type sits outside the fee market: a guardian's cancellation of a staged allocation spend (§10.2) cannot raise its own fee, so the mempool admits it without a fee contest, never evicts it, moves it to the front once its deadline is within a day, and lets nothing but another cancellation replace it. A flood of higher-paying traffic therefore cannot run out the 30-day veto window.

  • Keys. Every allocation output is a 34-byte Level V hashed vault (witness version 2) with no usable key path: its internal key is provably unusable.   • Staging and veto. Allocation coins can leave a vault only by being staged. A staged output can be released only after 86,400 blocks (about 30 days), and inside that window its guardians can cancel it back to the vault: 3 of 5 fund guardians for the stewardship fund, 1 of 3 per founder for that founder's vault. Consensus guarantees the public 30-day veto window; where a released output goes is the guardians' published policy, not a protocol rule.

11. Network protocol#

11.1 Transport and peers#

Spek runs on libp2p over QUIC only (encrypted with TLS 1.3, with stream multiplexing). Hosts on networks that block UDP cannot take part. Peers are found from a built-in bootstrap list, built-in DNS seed names, and a Kademlia random walk (frequent for ten minutes after start, then every ten minutes). A DNS answer only offers addresses to dial: at most half of a node's outbound connections come from it. A node lets go of a bootstrap node once it is synced to that node's exact tip and holds other peers, so bootstrap nodes keep room for nodes that are still joining. Every connection, however it was found, must pass diversity limits: at most one peer per IP address, at most a third of each direction's connections from one network group (13 inbound and 6 outbound on mainnet), at most 34% from hosting providers' networks (autonomous systems), 20 outbound and 60 in total on mainnet. Native IPv6 is not supported at launch.

11.2 Propagation#

Headers flood the network and are verified away from the event loop on a priority validation pool (signature 3–6 ms plus the reveal walk), with per-peer limits on work in flight, after the one-hash claimed-score filter has dropped any header that could not rank. Block bodies are pulled on request, never pushed. Seed-phase ticket records travel on their own topic and are checked at mempool priority, never on the slot-critical path.

Current-slot blocks are fetched compact-first: the serving peer sends short transaction ids keyed by a nonce it chooses, the receiving node rebuilds the block from its mempool and must arrive at the header's merkle root, and any failure falls back to requesting the full block. Full blocks remain the unconditional fallback and the path for initial download.

The scheduler serves the current slot's rank-1 block validation ahead of everything else: it has a reserved lane, then live propagation and catch-up share the next priority, then initial download, then mempool admission.

11.3 Misbehaviour#

Violations are counted per IP address (an IPv4 address written in IPv6 form counts as the same address), in three classes (header, transaction, block), each with its own threshold. Bans escalate 1 day → 4 days → 90 days, persist across restarts, and expire on the verified clock; a strike memory that survives expiry keeps a returning offender on the top rung. A ban for diverging across a checkpoint is capped at 16 days, so an honest node on the wrong side of a fork can always return.

Objective invalidity, such as a bad signature, a reveal outside its horizon or an invalid ticket record, is a strike. So is a header that builds directly on the receiving node's tip but is ineligible there, or carries an election seed that does not follow from the tip's: every node on that tip reaches the same verdict, and an honest node publishes a header only after checking it on its own tip. Five header strikes inside 18 hours ban the address. Drops that might be the relaying peer's fault rather than the producer's, or that depend on a ledger view that differs between forks, are silent and never strikes.

12. Synchronisation and checkpoints#

12.1 Initial block download#

A joining node downloads headers in batches and checks signatures and horizons in parallel, then fetches bodies in order and applies them strictly one at a time with the same block validation used at the tip, including each header's stake output or ticket record against the ledger built so far. Each candidate chain resolves its own beacons from its own headers.

Before switching to a candidate that forks below its tip, a node checks the candidate's headers whose stake had to exist before the fork point. For those heights every output or record that can count was created in the shared history, so the node checks each one against the ledger at the common ancestor, and every node reaches the same verdict. A candidate that fails is refused before anything is rolled back, and the peers that offered it are set aside. A fabricated chain therefore cannot force a synced node to unwind its own chain.

Every block at every height is fully verified, signatures included; there is no "assume-valid" height. Download starts only with at least 8 sync peers, or 1 if a built-in bootstrap node is connected, and no flag or RPC can lower that, so an attacker who surrounds a node with its own peers (an eclipse) cannot relax it. The node keeps mining and relaying while it waits.

12.2 Mining is never paused by download#

If a candidate chain could pause mining, an attacker could advertise a fake heavy chain to halt honest block production and exploit the weakened window. Mining on the main chain continues unconditionally; if the download finds a better chain, the switch to it orphans the node's own blocks in the normal way.

12.3 Checkpoints#

Checkpoints sit on the 4,000-block grid (§6.2). Hard checkpoints pin settled history for nodes that have none of their own (a new node, a resync, a node offline for days): peers' claims of chain weight are unauthenticated and could otherwise lock such a node onto a fabricated heavier chain. Unbonded stake cannot stop signing after the fact: a key that held stake at a fork point can sign a branch from that point at any later time, even after its owner sold the coins, and a private branch knows its own future beacons. Checkpoints are therefore permanent weak subjectivity, never retired.

Each release compiles in checkpoints the running network already holds as restoration pins, and between releases a pin file extends them. The node checks that file itself: it must name the network and genesis and carry signatures from a threshold of the checkpoint signers compiled into the binary, and it may add to the compiled-in table but never contradict it. Each signer confirms the hash on their own fully validated node, builds are reproducible, and every published pin can be checked independently.

13. Node and storage#

The reference implementation is a Rust workspace containing the node, a wallet, the miner key tool, the stewardship covenant and guardian tools, and an operator GUI.

State lives in RocksDB (headers, blocks with undo data, the UTXO set, the main-chain index, cumulative score, seed-phase ticket records, bans and snapshots), written in atomic batches without a disk flush per block; durability is recovered at checkpoint boundaries. The UTXO set is held in memory with an index by script and a value-ordered stake index for the eligibility check. A node runs in one of three modes: archive, pruned (the default, 100 GB target with a 20,000-block floor; pruned nodes can mine), or started from a UTXO snapshot. An archive grows by roughly 2 TB a year at full 2 MiB blocks; a pruned node needs around 15–20 GB plus about 0.7 GB of headers per year.

The node serves one authenticated JSON-RPC interface (port 4521) with integer-only values. It is not Bitcoin-compatible: there is no difficulty, nonce, bits field or median time; headers expose miner_pubkey, election_seed, horizon_start, slot_reveal and slot_path (the miner signature is in the raw block only), and getstakeaddress reports each horizon's stake address, eligibility window and counted output.

14. Governance and upgrades#

Spek has one upgrade mechanism: a block version that only increases, activated at a fixed flag height in a schedule compiled into the node and empty at launch. A signature-scheme or header-format change is always a hard fork and uses this path; tightening a rule uses it too, coordinated off chain. There is no version-bit signalling. Process governance is off chain and social; every full node enforces every rule; each operator independently adopts or declines an update.

Taken together, Spek offers:

  • no ASIC race;
  • no lock-up or slashing;
  • an ordinary computer is enough (the published minimum is 4 dedicated cores, 8 GB of RAM and an SSD);
  • one funded stake output keeps a key eligible for its whole 8.4-year horizon;
  • each stake unit gets exactly one draw per slot.

17. Known limitations and open items#

As of this version:

  • SQIsign is not a NIST standard. It is a Round 3 candidate in NIST's additional-signature process (§8.1). If later cryptanalysis weakens it, or NIST drops it, Spek's only remedy is a signature-scheme migration through a hard fork (§8.5, §14). Every operator chooses for themselves whether to adopt that fork.
  • No independent audit. The code, including the vendored SQIsign and RandomX C and the FFI boundary, has been audited only by AI models (Claude). No human security firm, cryptographer, or SQIsign author has reviewed it. Mainnet is its first exposure to outside attackers. The uniqueness of the slot reveal (§4.1) is the property most worth a cryptographer's time: a related hash-based construction for proof-of-stake election, X-VRF, was later broken on exactly that property.
  • Signing after the fact. Unbonded stake cannot stop a key that held stake at a fork point from signing a branch from that point later, including keys whose owners have since sold. Only restoration pins (running nodes) and compiled checkpoints (fresh nodes) bound it. On its own private branch an attacker also knows each beacon before that beacon's stake cutoff; simulation puts the break-even share at 0.45–0.47 for a branch inside the pin, and at about 0.42 (with a million candidate fits) for a fresh node that has no checkpoint past the fork.
  • Pins advance without network evidence. A restoration pin moves with the node's own tip, so a node partitioned, or mining alone, for longer than the pin lag (33–67 h) pins its own branch and refuses the other side on reconnect.
  • No fast finality. Settlement is by confirmations (Appendix B) until the pin; there is no finality gadget.
  • Download-time checks during the seed phase. Seed-phase eligibility needs the block bodies that hold the ticket records, so the header stage of a download checks signatures and horizons but no RandomX work. A fake seed-phase header chain is therefore as cheap to build as a fake post-seed one; the eligibility check before any rollback (§12.1), pins, block validation and the download's per-candidate budgets bound both.
  • Stake keys are hot and public. Every header shows its stake key, and the key lives on the mining machine. The payout rule keeps one stake unit per horizon at that address (two for the year before a renewal), and everything else goes to a hidden-key payout address. A node with no payout address configured keeps paying its stake address and warns daily.
  • Roughtime operator count. The built-in pool has four independent operators against a quorum of three: any one operator may be offline or rotating keys and syncs still complete, but with one offline every remaining operator must answer, and two colluding operators can steer the vote median (by at most the 5-second step bound per applied sync). The remedy is more independently operated servers, never a lower quorum.
  • Network-wide multi-slot outage stops the chain until an operator fills null blocks (§5). Single-node outages heal by themselves.
  • Withholding the top five. A node ranks at most five peer headers per slot plus its own (§5). If the five best headers of a slot are all withheld, every node that holds them settles the same canonical null: no body in the top five is committable, and a node's own block ranked sixth is skipped because no peer retains it, so committing it would leave each miner on a different block. Safety holds (one block per height; a node the withheld headers did not reach commits a real block, and any real block outranks the null), the slot's liveness is lost, and the withholder forfeits the slot's rewards. With an attacker share p of the draws for a slot, about p⁵ of slots are nulled; nulling a fraction f takes p = f^(1/5), that is p/(1−p) times the honest draw count: about 0.66× for 1% of slots, 1.7× for 10%, 6.7× for 50%. These are model estimates (independent uniform scores, every withheld header reaching every node), not simulation results. Each draw costs a recorded seed ticket per round in the seed phase and an aged stake output after it (§7).
  • Multiple draws per operator. One key per node is policy, not consensus. An operator holding K funded stake addresses (on one key or several) fields K draws for a one-time, refundable K × requirement. Whether the network's security then rests on capital held rather than on running costs turns on this, and it still needs a full economic analysis.
  • Not included: SPV proofs for light clients, native IPv6, data-availability sampling, on-chain soft-fork signalling, verification of a UTXO snapshot after sync, and NTS (authenticated NTP).
  • Hard checkpoints are a permanent trust assumption for nodes with no history of their own (weak subjectivity): such a node trusts the release's compiled-in pins and the checkpoint signer set. They have no sunset; the signer set, its threshold and the signing procedure are part of the launch disclosure.
